# RehabMind v3 数据与工作流合同

## 目标

v3 将“临床事实、流程状态、页面草稿和身份历史”分开保存，解决 v2 中页面游标、动态处理队列和业务结果混在同一快照里的问题。处理候选仍可以动态重排，但已经产生的评估、处理和复查事实不能随页面队列消失。

本次是干净切换。当前没有需要保留的真实用户数据，因此不提供 v1/v2 到 v3 的业务数据迁移，也不补猜旧记录。

## 持久化结构

所有服务器 API、IndexedDB、本机草稿和导出文件只接受 `schemaVersion: 3`，并使用以下四段结构：

| 分段 | 保存内容 | 不应保存的内容 |
|---|---|---|
| `identity` | 案例、康复问题、康复次数、开始和完成时间、历史索引 | 页面按钮状态、处理排序 |
| `domain` | 问诊、安全答案、评估、处理、复查、训练和历史结果 | 当前卡片序号、临时展开状态 |
| `workflow` | 当前阶段、评估/方案修订号、待复查数、异常反应状态 | 可由领域事实重新计算的候选详情 |
| `draft` | 未提交的页面选择、当前评估和处理游标、临时复测输入 | 已确认的临床结论 |

工作台目前仍通过兼容适配器把嵌套 v3 解码为页面内存态。该内存态不能直接跨越持久化边界；写入前必须调用 `persistSavedDemoSnapshot()`。

## 核心不变量

1. `identity.problemThreadId` 必须存在于 `identity.problemThreads`。
2. `identity.sessionId` 必须存在于 `identity.sessionIndex`，并属于当前案例和当前康复问题。
3. `workflow.pendingRetestCount` 必须等于 `domain.retests.obligations` 中必需且待完成的数量。
4. 普通问诊编辑不得新建康复问题、康复次数或归档事件。
5. 只有明确的“出现新问题”操作可以调用 `startNewProblemThread()`。
6. 处理队列为空不等于处理阶段完成；仍有必需复查时必须停留在处理复查阶段。
7. 一项处理可以关联多个复查，但不同评估、不同侧别的复查不能互相覆盖。
8. API 不接受扁平 v3、v1 或 v2 快照，也不在服务端迁移或补齐旧字段。

## 复查台账与页面队列

复查使用独立 `RetestObligation` 和 `RetestRecord`：

- 义务记录“还欠什么”，ID 在同一康复次数内稳定。
- 结果记录“实际复查了什么”，只追加已确认事实。
- 活动范围、功能动作、主诉动作和训练安全复核使用不同类型。
- 双侧项目按左、右拆成两个义务。
- 专业工作台可以查看完整复查台账；普通模式只提示用户还需要完成哪些动作。

处理候选仍使用动态队列，因为它需要按新证据重排。评估项目仍使用有序清单，因为顺序服务于页面操作。已经发生的临床结果使用台账，因为它需要稳定身份、完成状态和审计关系。

## 控制器边界

工作台状态按职责拆分：

- `useAssessmentFlow`：评估答案与评估游标。
- `useTreatmentFlow`：处理、范围复查和处理游标。
- `useTrainingFlow`：训练反馈与训练阶段状态。
- `useRehabSession`：当前康复次数及历史。
- `useDecisionEngine`：规则投影入口。
- `useWorkflowController`：阶段解锁和完成门槛。

组件负责展示和触发用户操作，不应另建一份平行的业务事实状态。

## 本机存储切换

IndexedDB 版本为 3。首次从旧数据库升级时清空旧案例和旧草稿，并改用 v3 本机键。用户数据和 `/test` 数据继续按 scope 隔离。

浏览器端不迁移旧快照；旧版本恢复失败时应要求用户刷新并新建记录，不能把旧页面字段复制成 v3 临床事实。

## 运行数据清理与回滚

默认审计，不修改数据库：

```bash
npm run data:v3:reset
```

确认后执行：

```bash
npm run data:v3:reset:apply
```

执行脚本会先做 WAL checkpoint，再生成时间戳 SQLite 备份并验证备份可读，随后在事务中清理案例、快照、事件、反馈、试用事件和管理审计等运行数据。知识库、决策发布记录和迁移登记保留。

如需回滚，先停止所有写入服务，再用脚本报告的备份文件替换当前 SQLite 文件。替换后必须重新执行 `PRAGMA integrity_check` 和 `PRAGMA foreign_key_check`。

## 发布边界

- v3 代码发布与旧运行数据清理是两个独立动作。
- 必须先通过类型、架构边界、Lint 和正式 build，再提交生产代码。
- 清理前确认没有进程写 SQLite；清理后验证运行表为空、知识和发布表仍保留。
- QA 测试合同、截图基线和测试证据不属于本开发提交。
