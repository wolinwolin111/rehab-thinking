# RehabMind 会话内核与规则发布架构重构计划

> 文档状态：待规则审核后启动实施  
> 建立日期：2026-08-29  
> 适用范围：RehabMind 正式下肢流程  
> 第一阶段试点：大腿＋膝  
> 开发与测试边界：本文只定义生产架构、开发合同和测试接缝；QA 测试方案、断言、证据及执行由独立测试会话自行判断。

## 1. 执行结论

当前项目需要重构，但不适合整体推倒重写。建议采用“选择性纵向重构”：以一条完整的大腿＋膝业务纵向切片建立新的会话内核、规则执行和发布版本体系，验证可行后再逐区域迁移。

这次重构不以“主组件变短”“抽出更多函数”或“增加更多 core 文件”为成功标准。过去的重构已经降低了静态文件耦合，却没有消除运行时的多事实源：页面状态、动态处理队列、复查台账、历史投影和保存快照仍可能分别解释同一业务事实。新的完成标准是：

1. 一项用户操作只有一个正式命令入口。
2. 一类业务事实只有一个所有者。
3. 页面只显示聚合根生成的 `ScreenModel`，不重新推导业务结论。
4. 处理队列只安排顺序，不拥有评估事实或复查义务。
5. 保存、恢复、刷新和页面返回不能产生新事实或改变确认时间。
6. 每个会话固定规则发布版本，规则升级不能静默重算历史。
7. 迁移一个纵向切片后删除对应旧路径，不长期双写。

## 2. 为什么现有优化没有减少流程问题

现有项目已经做过目录分层、纯函数抽取、Hook 抽取和专项 decision core 拆分。这些工作有价值，但主要解决“代码放在哪里”和“函数能否单测”，没有统一“运行时谁有权决定事实”。

当前主要问题不是函数数量少，而是同一结论存在多条生成路径：

- 评估结果既存在正式记录，也存在 React 临时状态和专项 core 投影。
- 处理候选既来自关系表，也来自内容库、专项决策和页面补充过滤。
- 功能复查义务既可能附着在动态候选，又可能从台账重算。
- 流程门槛、处理页和总结页可能读取不同来源。
- 第二次康复可能把首诊事实重新标注为新会话事实。
- 保存函数可能在投影过程中重新生成 ID 或时间。

继续仅抽函数会让依赖更分散，继续仅补判断会让状态组合增加。需要改变的是业务状态模型和写入权限，而不是再增加一层工具函数。

## 3. 重构边界

### 3.1 本轮必须改变

- 正式会话建立单一聚合根。
- 用户操作改为显式命令。
- 正式事实、派生投影和页面草稿分离。
- 复查台账成为唯一复查事实源。
- 阶段推进和安全停止由聚合根硬门槛控制。
- 规则内容进入可审核、可编译、不可变的规则包。
- 数据库记录规则发布、审核、启用和回滚，不直接按可变行临时拼装临床规则。
- 每个会话固定规则版本和数据合同版本。

### 3.2 本轮不做

- 不一次迁移所有身体区域。
- 不在规则审核前重写具体临床关系。
- 不把页面草稿全部事件化。
- 不将每次滑杆移动、展开卡片或导航点击写成领域事实。
- 不为当前测试数据设计复杂迁移；目前无真实用户数据，允许备份后清空不兼容运行数据。
- 不由开发会话重写 QA 浏览器用例或视觉基线。

## 4. 目标架构

```text
用户操作
  ↓
Command
  ↓  校验会话、角色、安全、当前修订和规则版本
RehabSessionAggregate
  ├─ 追加 Domain Facts
  ├─ 更新 Task Projection
  ├─ 执行 Safety / Workflow Invariants
  └─ 生成 Decision Trace
  ↓
ScreenModel
  ↓
React 页面只负责展示与收集草稿

Rule Release
  ├─ 结构化规则组件
  ├─ 编译后的执行包
  ├─ schemaRevision
  ├─ bundleHash
  └─ 审核与发布记录
```

核心数据流固定为：

```text
Command → Facts → Task Projection → ScreenModel
```

任何页面都不得绕过这条链路直接修改正式事实，也不得根据标题、标签、数组位置或当前页面阶段重新生成业务结论。

## 5. RehabSessionAggregate 单一聚合根

### 5.1 身份边界

聚合根最小身份：

- `caseId`
- `problemThreadId`
- `sessionId`
- `sessionNumber`
- `ruleReleaseId`
- `schemaRevision`
- `bundleHash`
- `aggregateRevision`

同一案例可以拥有多个问题线程；每个问题线程可以拥有多次康复会话；每次会话使用独立聚合根。历史会话完成后只读，不能被当前页面重新标注。

### 5.2 聚合根拥有的正式事实

- 问诊确认事实；
- 安全确认、停止、医学许可和重新确认事实；
- 评估记录及修订；
- 处理记录；
- 复查义务与复查记录；
- 训练计划、反馈和加重 episode；
- 会话完成事实；
- 显式答案修改和失效关系；
- 决策追踪所引用的事实 ID。

### 5.3 聚合根不拥有的内容

- 卡片展开状态；
- 当前滚动位置；
- 尚未确认的文本和滑杆草稿；
- 纯展示排序；
- 网络在线状态、同步重试计数和弹窗状态；
- 规则文案本身。

这些内容分别属于页面草稿、展示投影或基础设施状态，不能反向成为临床事实。

## 6. 三类状态严格分离

| 类型 | 示例 | 写入时机 | 是否持久化 | 是否可作为决策事实 |
|---|---|---|---|---|
| 正式事实 | 已确认下蹲疼痛、处理完成、复查仍受限 | 用户点击确认命令且校验通过 | 是，追加式 | 是 |
| 派生投影 | 待复查数、当前任务、可进入训练、总结文案 | 由事实＋固定规则版本纯计算 | 可缓存，不是事实 | 只能作为展示和门槛投影 |
| 页面草稿 | 滑杆当前位置、输入框未提交内容、展开项 | 用户交互即时变化 | 可选本地暂存 | 否 |

禁止事项：

- 从页面草稿直接生成总结。
- 保存快照时把草稿时间当作事实确认时间。
- 从历史投影复制出当前会话评估。
- 从处理队列反推评估是否存在。
- 用“页面已经到第4步”证明前置业务已经完成。

## 7. Command 合同

第一阶段至少建立以下命令：

| Command | 主要输入 | 主要前置 | 追加事实/结果 |
|---|---|---|---|
| `ConfirmIntake` | 结构化问诊草稿 | 当前会话可编辑 | 问诊确认事实、评估任务投影 |
| `ConfirmSafety` | 安全答案、影像、许可 | 问诊已确认 | 安全事实或停止事实 |
| `RecordAssessment` | assessmentId、side、答案、revision | 安全允许、任务有效 | 评估事实、复查义务、候选投影 |
| `AmendAssessment` | 原事实ID、新答案、原因 | 显式编辑确认 | 原事实失效标记、新修订事实、新义务 |
| `CompleteTreatment` | treatmentTaskId、处理草稿 | 任务有效、权限满足 | treatmentRecord、活动/主诉复查义务 |
| `RecordRetest` | obligationId、结果 | 义务有效且属于当前会话 | 新 retestRecord、义务状态投影 |
| `RecordTrainingFeedback` | trainingTaskId、反馈 | 训练任务开放 | 反馈事实或加重 episode |
| `ResolveTrainingWorsening` | episodeId、出口 | episode 未关闭 | 处理/退阶/停止事实 |
| `SaveDraft` | 聚合根修订 | 无业务推进 | 只序列化，不新增临床事实 |
| `CompleteSession` | 当前修订 | 所有硬门槛满足 | 会话完成事实 |
| `StartFollowupSession` | problemThreadId | 前次会话存在 | 新 sessionId 与固定规则版本 |
| `StartNewProblemThread` | 新问题问诊草稿 | 显式新问题入口 | 原子归档旧线程并创建新线程/会话 |

命令处理必须在一个事务边界内完成：校验前置、追加事实、重建任务投影、执行不变量、递增修订。禁止用多个 React setter 和后续 `useEffect` 拼出一项业务操作。

## 8. 复查台账唯一事实源

### 8.1 义务生成

- 功能动作实际完成且有不适、评分或控制异常：建立普通功能复查义务。
- 因疼痛或没力实际尝试但做不完：建立“现在能否完成”的状态复查义务。
- 因害怕、没听懂或未尝试：生成补评估/说明任务，不生成伪前后复查。
- 活动范围处理与异常方向明确关联时：建立该方向独立复查义务。
- 处理明确针对可重复主诉时：建立主诉复查义务。
- 每次训练加重：建立独立训练安全 episode。
- 肿胀、肌腱次日反应等：建立带计划时间的延后观察义务。

### 8.2 稳定身份

义务身份至少包含：

```text
sessionId + assessmentId + side + assessmentRevision + kind
```

处理记录每次执行生成新的 `treatmentRecordId`；复查每次确认生成新的 `retestRecordId`。正常重复形成时间序列，更正错误答案通过 `supersededAt / supersededBy / reason` 失效，不覆盖历史。

### 8.3 队列的职责

处理队列可以：

- 根据规则和权限安排处理顺序；
- 把多个问题映射到同一次执行；
- 在安全条件改变时暂停或重排；
- 决定何时展示某项复查。

处理队列不可以：

- 创建或删除功能复查义务；
- 用候选是否存在判断评估是否需要复查；
- 在候选完成后带走未完成义务；
- 用数组序号作为处理或复查身份；
- 让一侧结果覆盖另一侧。

队列为空但当前修订仍有必需复查时，聚合根必须生成“剩余动作复查”任务，禁止进入训练或总结。

## 9. 安全和流程硬门槛

以下条件属于应用内核不变量，规则包和页面都不能放宽：

- 未完成最低安全确认不能进入负荷评估或处理。
- 命中停止信号后不能继续普通评估、处理和训练。
- 需要专业权限的操作必须校验当前角色与必要前置。
- 当前修订存在待补评估时不能完成处理阶段。
- `pendingRequiredRetestCount > 0` 时不能进入训练或总结。
- 存在未关闭训练加重 episode 时锁定其他动作反馈和进阶。
- 双侧任务必须按侧独立完成，优先侧不能覆盖另一侧。
- 会话完成命令必须重新校验全部不变量，不能只相信页面阶段。

阶段导航是 `ScreenModel` 的展示结果，不是完成事实。`maxUnlockedStage` 只能由聚合根根据任务和安全状态计算。

## 10. 规则架构：规则包、执行器、发布数据库

### 10.1 规则包

规则包保存经过审核的结构化内容：

- 稳定规则 ID 和组件版本；
- 适用部位、动作、症状和角色；
- 必需输入和禁止条件；
- 评估任务及依赖；
- 处理适用证据、权限和停止条件；
- 复查义务模板；
- 训练准入和进退阶条件；
- 用户文案引用；
- 来源、证据等级和审核结论。

规则包不能拥有会话事实，不能改变应用硬门槛，也不能依赖页面标题或中文包含匹配作为正式主键。

### 10.2 规则执行器

执行器接收：

```text
当前有效事实 + 当前任务状态 + 固定 RuleRelease
```

输出：

- 新增/取消任务建议；
- 候选与排除原因；
- 复查模板；
- 训练建议；
- 决策追踪。

执行器必须是确定性的：相同事实和相同发布版本得到相同输出。它不能读取 React state、当前系统时间、数据库可变规则行或网络状态。时间由命令层作为显式输入。

### 10.3 发布数据库

建议表结构：

| 表 | 作用 | 关键约束 |
|---|---|---|
| `rule_releases` | 发布ID、schemaRevision、bundleHash、源码提交、状态、建立时间 | 发布后不可修改内容 |
| `rule_release_components` | 发布包含的规则组件ID、类型、版本、组件哈希 | 同一发布内组件唯一 |
| `rule_release_reviews` | 审核角色、范围、结论、审核人和时间 | 结论追加，不覆盖历史 |
| `rule_channel_heads` | 各环境/渠道的新会话启用版本 | 只切指针，不改历史会话 |
| `rule_release_audit` | 编译、发布、启用、停用、回滚和紧急处置 | 追加式审计 |

规则正文保存在编译生成的不可变发布包中。数据库负责登记、审核和选择版本，不允许运营人员临时编辑几行数据库后组成新的运行规则。

## 11. 会话规则版本固定

每次会话创建时写入：

```text
ruleReleaseId + schemaRevision + bundleHash
```

并遵守：

- 新规则默认只影响新会话。
- 进行中会话继续使用原规则版本。
- 历史总结始终使用原版本投影或已保存的最终投影。
- 回滚只切换 `rule_channel_heads`，不重算历史。
- 启动或恢复时哈希不匹配立即拒绝加载。
- 紧急安全问题通过应用硬门或明确发布新版本处理，不静默改写旧事实。

## 12. 数据模型和持久化

### 12.1 推荐存储边界

- `session_aggregates`：当前聚合根快照、修订、规则版本和完成状态。
- `session_facts`：追加式业务事实；按 case/thread/session、事实类型和来源 ID 索引。
- `session_tasks`：可重建任务投影；必要时持久化以支持查询和恢复校验。
- `decision_traces`：输入事实、规则命中、排除原因、任务输出和规则版本。
- 规则发布五张表：独立于会话运行数据。

不要求立刻采用完全事件溯源。建议使用“追加事实＋可重建快照”的折中方案：写命令时同时追加事实并更新聚合快照；恢复时优先加载快照，再用版本和一致性检查验证。快照不是第二事实源。

### 12.2 扩展性

- 所有记录携带 `caseId/problemThreadId/sessionId`，支持同一案例多问题、多会话。
- 稳定 ID 不包含数组位置或用户文案。
- `regionId/actionId/assessmentId/ruleId` 使用受控代码表。
- 通过事实类型和规则组件扩展新区域，不增加新的平行会话内核。
- 数据库索引围绕会话读取、待办查询、事实来源和规则版本建立，不围绕页面步骤建立。

### 12.3 当前数据处理

目前没有需要保留的真实用户数据。实施不做复杂 v2/v3 临床事实迁移：

1. 先生成数据库和本地存储一致性备份。
2. 清空不兼容运行案例、草稿和测试夹具数据。
3. 升级本地存储版本，拒绝旧合同恢复。
4. 规则发布和结构迁移脚本保留可重复执行及回滚能力。

备份用于故障恢复和审计，不将旧测试答案猜测为新事实。

## 13. 第一阶段纵向切片：大腿＋膝

选择大腿＋膝的原因：

- 同时包含局部肌肉、关节活动、力量、功能和动作控制。
- 包含坐站、下蹲、台阶、单腿等不同负荷层级。
- 能覆盖单侧、双侧、处理合并和多项复查。
- 现有显式关系和专项 core 都较丰富，足以验证规则归一。
- 比一次纳入踝足急性、安全和肌腱/骨应力分支更易控制试点风险。

试点必须走通：

1. 新建问题并固定规则版本。
2. 问诊和安全确认。
3. 大腿＋膝评估任务生成。
4. 功能异常立即建立复查义务。
5. 处理与活动、功能复查合并展示但分别保存。
6. 双侧逐侧评估、处理和复查。
7. 训练反馈、加重锁定和退出。
8. 总结只读取当前会话事实。
9. 保存、刷新、恢复不改变 ID 和时间。
10. 第二次康复只产生本次实际确认事实。

## 14. 分阶段实施计划

### 阶段0：冻结边界与规则审核

- 完成规则审核 Excel 中第一阶段所有运行项。
- 给每项规则指定唯一所有者、结论和专业审核状态。
- 决定问诊事实、评估原语、处理原语和复查原语。
- 冻结第一版 `RuleRelease` 输入合同。

完成门槛：当前运行规则没有未归属来源；所有 `revise/hold/retired` 有处理决定；未审核规则不能参与试点。

### 阶段1：建立聚合根和事实合同

- 建立身份、正式事实、任务、命令和不变量类型。
- 建立无副作用序列化/恢复。
- 建立命令事务和聚合修订冲突检查。
- 不接页面，先用纯逻辑场景验证。

完成门槛：相同命令序列得到相同事实和投影；恢复前后哈希一致；保存不新增临床事实。

### 阶段2：规则包和执行器

- 把已审核的大腿＋膝规则编译为第一版组件。
- 建立规则引用、冲突、空复查目标和悬空 ID 检查。
- 建立不可变发布包和决策追踪。
- 登记开发环境 RuleRelease。

完成门槛：规则包编译确定；任何未审核或悬空规则导致发布失败；执行器不依赖页面和数据库可变行。

### 阶段3：问诊、安全与评估纵向接入

- 页面改用命令和 ScreenModel。
- 移除该切片页面内重复关系匹配和阶段解锁判断。
- 评估确认立即生成稳定事实和功能复查义务。
- 建立显式答案修改及失效链。

完成门槛：新问题不继承旧评估；第二次康复不复制首诊事实；功能义务不依赖处理候选。

### 阶段4：处理、复查与训练纵向接入

- 处理队列只作为任务排序投影。
- 活动范围、功能和主诉复查读取同一台账。
- 多项/双侧结果独立计算。
- 训练加重 episode 进入聚合根硬门槛。

完成门槛：范围＋功能组合场景无漏项；队列空但复查未完成时不能进训练；重复处理和复查保留历史。

### 阶段5：总结、保存、恢复和历史

- 总结只读取当前会话有效事实。
- 保存/冲突/恢复只处理聚合快照和基础设施状态。
- 后续康复、新问题线程完成原子命令接入。
- 决策追踪可回读规则版本和输入事实。

完成门槛：刷新、自动保存、多标签冲突不改变事实时间；历史会话不被新规则重算。

### 阶段6：删除旧路径并评估扩展

- 删除大腿＋膝切片对应的旧页面推导、动态义务生成和重复决策路径。
- 使用依赖检查确认不存在正式调用方。
- 评估是否继续迁移小腿＋踝足。

完成门槛：同一业务事实只剩一个写入口；无长期双写、双读或隐藏回退。

## 15. 禁止长期双写

迁移期间只允许短期、只读的“影子比较”：旧引擎与新内核接收同一已确认输入，记录差异，但只有一个结果进入正式事实。禁止：

- 同时写旧快照和新事实后长期维持。
- 页面失败时静默退回旧业务判断。
- 为了让旧测试通过保留两套复查完成条件。
- 新内核结果和旧页面结果互相补字段。
- 以 feature flag 无限期保留双路径。

每个切片开始前必须定义旧代码删除清单；阶段完成必须执行删除，否则不进入下一部位。

## 16. 停止与继续硬门槛

### 16.1 可以继续下一阶段的条件

- 当前阶段的单一事实源已经建立。
- 旧写路径已删除或完全不参与正式运行。
- 序列化/恢复前后事实、ID、时间和规则版本一致。
- 不变量可以拒绝非法阶段推进、跨会话引用和悬空义务。
- 决策追踪能解释候选进入与排除。
- 开发合同检查、类型检查、Lint 和正式 build 通过。

### 16.2 必须停止的条件

- 仍需要页面读取两套来源才能完成流程。
- 规则审核未决项会改变事实模型或安全门。
- 新旧路径对同一输入给出不同安全结论且原因不明。
- 为兼容旧代码开始增加新的临时 ID、时间或数组序号映射。
- 第二次康复或新问题仍会继承旧事实。
- 无法证明历史会话固定使用原规则版本。
- 为赶进度准备修改 QA 断言掩盖生产差异。

触发停止条件时，保持最近一个可回退提交，不扩大迁移范围。

## 17. 规则审核对重构的影响

### 17.1 不受具体规则结论影响的稳定骨架

- 聚合根身份和事务边界；
- Command → Facts → Task Projection → ScreenModel；
- 正式事实、投影、页面草稿分离；
- 复查台账唯一事实源；
- 追加记录和失效标记；
- 会话固定规则发布版本；
- 规则发布不可变和历史不重算；
- 安全与流程硬门槛归属应用内核。

这些内容可以先设计和建立类型合同。

### 17.2 必须等待审核结论的内容

- 规则组件字段和审核状态枚举；
- 位置、动作、症状和证据原语；
- 每条关系的 `all/any` 触发语义；
- 评估任务依赖图和预算；
- 处理适用证据、权限、顺序和停止条件；
- 复查义务模板；
- 训练准入和进退阶；
- 部分 Command 的必填业务字段。

因此，审核不会推翻重构方向，但会直接影响规则包 schema 和任务依赖。正确顺序是先完成规则审核，再冻结首个执行合同，不能先按现行分散代码反向固化所有字段。

## 18. 风险与收益

| 事项 | 风险/成本 | 预期收益 | 控制方式 |
|---|---|---|---|
| 建立聚合根 | 初期类型和命令数量增加 | 消除多事实源和跨阶段补丁 | 先做大腿＋膝纵向切片 |
| 追加事实 | 存储和查询复杂度提高 | 保留修改、重复处理和时间序列 | 快照＋事实折中，不追求全事件溯源 |
| 规则发布版本 | 增加编译、审核和发布流程 | 历史可解释、可回滚、不漂移 | 五张发布表＋不可变包 |
| 删除旧路径 | 短期回归风险 | 防止双写长期恶化 | 每阶段独立提交和删除清单 |
| 规则先审核 | 推迟部分编码 | 避免把错误现行行为固化为新架构 | 两阶段审核，先下肢后未开放区域 |
| 页面只读ScreenModel | 需要改造现有 props 和 state | 页面不再拥有业务判断 | 按阶段逐页接入 |

总体性价比：中长期高，短期成本中高。若项目继续扩展身体区域、第二次康复和规则发布，这项重构是必要基础；若仅保留当前演示且不再扩展，收益会下降。

## 19. 工作量估算

在规则审核及时完成、当前无真实数据迁移负担的前提下：

- 架构试点（大腿＋膝）：约 8～11 个开发日。
- 规则包和发布数据库完善：约 4～7 个开发日，可与部分试点并行。
- 小腿＋踝足迁移：约 5～8 个开发日。
- 全部正式下肢收口、旧路径删除和交接：整体约 3～5 周。

工作量不含 QA 独立回归周期、临床专业审核等待和新解剖素材制作。若规则审核导致评估/处理原语大幅改变，应重新估算阶段2～4。

## 20. 开发验收与 QA 交接边界

开发侧负责：

- 领域类型和不变量合同；
- 规则包编译、引用和发布检查；
- 聚合根命令场景检查；
- 无副作用序列化/恢复检查；
- 稳定 fixture/test-only 接缝；
- TypeScript、Lint、正式 build；
- 每批生产提交、schemaRevision、ruleReleaseId、bundleHash 和变更说明；
- 开发完成后的测试交接文档。

开发侧不负责：

- 修改 QA 断言制造通过；
- 替测试会话决定完整测试策略；
- 提交 QA 浏览器证据、视觉基线或质量文档；
- 把开发场景检查冒充正式回归结果。

用户会在开发完成后将交接材料自行发送给测试会话。测试会话应基于新事实模型独立判断哪些旧测试保留、重写或退役，不要求机械照抄旧页面流程。

## 21. 最终完成定义

只有以下条件全部满足，才可宣称架构重构完成：

1. 正式下肢所有当前会话操作经过聚合根命令。
2. 评估、处理、复查、训练和历史各有唯一事实源。
3. 页面不再生成临床事实或重新解释完成状态。
4. 处理队列不拥有复查义务。
5. 保存和恢复无副作用。
6. 多会话、多问题、双侧和答案修改均保持身份与历史。
7. 每个会话固定不可变规则版本，规则回滚不重算历史。
8. 对应旧路径已删除，没有长期双写和隐式回退。
9. 数据合同、规则包和发布记录可追踪到源码提交与审核结论。
10. 开发合同检查、类型检查、Lint、正式 build 通过，并已形成独立 QA 交接。

这十项比文件行数、函数数量或目录层级更能判断本次重构是否真正解决了流程打补丁问题。
