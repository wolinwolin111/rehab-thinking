# REHABMIND 试用持久化测试文档

## 1. 文档目的

本文件记录邀请制小范围试用所需的持久化、恢复、案例隔离、反馈绑定和复现测试要求。它是本地实现、预览环境和正式试用环境的验收依据。

本项目不使用 AI 做康复决策。现有康复规则、评估流程和安全退出逻辑已经有独立测试覆盖；本文件新增的测试只验证案例数据是否被正确保存、恢复、读取和追溯，不重新证明既有决策规则。

## 2. 测试分层

### 2.1 数据层

- D1 迁移可以在空数据库中创建全部试用表。
- 迁移重复执行不会破坏已有数据。
- 案例编号唯一，案例快照与事件只能归属于一个案例。
- 案例删除或失效后的数据处理符合隐私约定。
- 快照修订号单调递增，事件序号单调递增且不重复。
- 快照、事件、反馈的外键关系正确，跨案例引用被拒绝。

### 2.2 应用服务层

- 创建案例时生成不可预测的匿名案例编号和访问凭据。
- 数据库只保存访问凭据的摘要，不返回或记录原始凭据。
- 保存快照时校验案例归属、访问凭据和期望修订号。
- 重复提交同一个事件不会产生重复事件。
- 并发保存或旧页面保存会得到修订冲突，而不会覆盖新快照。
- 事件保留原始输入、解析结果、用户确认和系统推导的独立字段，不把它们混成一个不可追溯结果。
- 反馈必须绑定案例；可以绑定到具体康复记录、流程阶段或“未定位”，并单独保留提交反馈时所在的记录和阶段。
- 每次写入记录应用版本、知识版本和决策版本。
- 一个案例的读取、保存和反馈不会影响另一个案例。

### 2.3 接口层

- 缺少必要字段、非法修订号、非法事件类型和过大的无效载荷返回明确的 4xx 错误。
- 无效访问凭据、失效案例编号和跨案例访问不会泄露案例内容。
- 重试请求返回幂等结果，不新增重复事件。
- 服务器错误不会把访问凭据、完整用户主诉或内部堆栈写入公开响应。
- 读写响应包含当前修订号和版本信息，便于页面恢复和后台复现。

### 2.4 浏览器流程层

- 用户创建案例后，关键节点自动保存。
- 刷新页面后可以恢复最近一次成功保存的完整流程。
- 两个案例交替操作时，输入、快照和反馈不串线。
- 网络失败时页面保留本地草稿并显示可理解的保存状态，不假装已经写入服务器。
- 重复点击保存、快速连续保存和刷新中断保存不会造成重复案例或重复事件。
- 删除或失效后的旧链接不能重新读取案例。
- 后台读取到的流程顺序与用户实际操作顺序一致。

## 3. 必测场景

1. 新建案例，写入 `case_created`，读取案例编号和访问凭据。
2. 保存一个完整快照，再保存下一修订，确认修订号为 `0 → 1 → 2`。
3. 用旧修订号保存，确认返回冲突且当前快照不变。
4. 用同一个事件编号重试，确认事件总数不增加。
5. 用同一个事件编号提交不同内容，确认请求被拒绝。
6. 创建两个案例，交叉保存并读取，确认数据完全隔离。
7. 分别提交当前模块反馈、历史康复记录反馈和“暂不确定具体环节”反馈，确认目标位置、提交位置、案例和事件关系正确。
8. 模拟超时、双窗口、刷新中断和部分写入失败，确认不会生成半条不可恢复的进度。
9. 使用缺失字段、非法编号、非法凭据和损坏快照，确认得到可识别错误。
10. 读取案例时间线，确认原始输入、解析、确认、评估、处理、复测、训练反馈和总结可以按序复现。

### 正式试用环境

- 邀请链接、管理员入口保护、用户反馈、案例删除、基本错误日志和当前版本标识通过。

- 通过后才向粉丝群开放。

## 5. 基线与范围控制

- 406 个是本文件早期执行记录；当前最新的规则和流程回归基线为 494 条，统一以[最新测试计划](./rehabmind-test-plan.md)为准。
- 本文件不要求重复测试没有改动的康复决策逻辑。
- 不在本阶段加入 AI 决策、复杂账号体系、多人协作、微服务、实时通信或新的大范围关节内容。
- 测试数据使用合成案例，不使用真实身份信息。
