# 12 多部位、多关节重构与 AI 主诉收集方案

> 状态：下一版目标方案，尚未完整进入当前 Demo  
> 版本：2026-08-13  
> 首批范围：下肢，大腿至足部；优先验证膝与踝足组合  
> AI 边界：只负责症状主诉信息的收集、整理和缺项追问，不负责评估、处理、训练或医学判断

## 1. 为什么需要这次重构

真实主诉不一定严格落在一个关节，也不一定只有一个发生时间：

- 同一次崴脚可能同时出现踝、足和膝部症状；
- 用户可能说大腿、小腿、足底或脚背不舒服，而不是说某个关节；
- 旧踝伤长期未恢复，之后可能出现膝部症状；
- 多个位置可能属于同一个功能问题，也可能是两个独立问题；
- 用户通常只能描述事实，无法判断“是否代偿”或“哪个组织有问题”。

当前 Demo 仍以第一个 `regionId` 驱动完整流程。继续增加条件分支容易造成：

- 第二区域信息混入第一区域处理；
- 检查数量成倍增加；
- 相同肌肉、动作和复测重复出现；
- 不同问题的结果和康复次数互相污染；
- 单次没有即时减痛，就错误否定长期代偿假设。

因此目标不是“同时运行两套单关节问卷”，而是建立一个病例层调度器，在同一病例内管理多个发生事件、问题链和可能关系。

## 2. 总体原则

1. 多部位输入不等于多关节流程。
2. 用户只陈述事实，系统负责整理主次、时间线和待验证关系。
3. 当前最影响生活或最需优先确认的问题，一次只运行一条主流程。
4. 相邻关节先做少量高相关筛查，不默认展开完整评估。
5. 局部症状处理、上游能力恢复和多关节功能训练可以同时存在。
6. 单次即时反应只验证当场可改变的指标；复杂代偿主要看多次趋势。
7. AI 不产生诊断，不决定评估、处理、训练或安全分流。
8. 不确定信息保持未知，不能由 AI 或规则补成确定事实。

## 3. 多部位场景怎样归组

### 3.1 一个问题涉及多个位置

示例：下楼时膝内侧痛，同时大腿外侧紧。

- 主问题：下楼时膝内侧痛；
- 相关位置：大腿外侧；
- 只建立一条主诉问题链；
- 大腿外侧作为检查和处理候选，不自动启动完整髋关节流程。

### 3.2 同一事件造成多个独立问题

示例：崴脚摔倒后外踝肿胀，同时膝前直接撞地疼痛。

- 事件相同；
- 踝和膝分别建立问题链；
- 先处理安全性、急性程度和生活影响更高的问题；
- 第一条问题链完成阶段性结论后，再进入第二条。

### 3.3 不同时间但可能存在代偿关系

示例：三个月前右踝扭伤，背屈一直偏小；最近两周右膝下楼疼。

- 旧踝伤和近期膝痛分别保存；
- 两者之间建立“可能相关、待筛查”的关系；
- 当前膝痛仍需完成膝局部评估；
- 旧踝先做与下楼功能相关的短筛查，不运行急性崴脚全流程；
- 不能直接表达为“踝关节导致膝痛”。

### 3.4 不同时间且当前没有关系线索

示例：半年前左膝跑步痛，同时近期右足趾被鞋挤压疼痛。

- 分别建立问题；
- 没有同侧、同动作、功能链或先后变化线索时，不强行建立代偿关系；
- 首批一次康复最多激活两条问题链，其余问题保存后另行处理。

## 4. 数据结构

```text
RehabCase
├─ rawNarrative                 用户原始描述
├─ confirmedFacts               用户确认后的病例事实
├─ episodes[]                   发生事件与时间线
├─ problemChains[]              当前需要解决的问题链
├─ relationships[]              问题之间的待验证关系
├─ activeProblemChainId         当前唯一执行的问题
├─ sharedFunctionalTasks[]      多问题共同涉及的功能动作
└─ sessionHistory[]             每次康复记录
```

### 4.1 发生事件 `Episode`

```ts
type Episode = {
  id: string;
  timeText?: string;
  onsetOrder?: number;
  mechanism?: string;
  involvedSites: SymptomSite[];
  acuteFindings: string[];
  imagingFacts: ConfirmedImagingFact[];
  source: "user-explicit" | "user-confirmed";
};
```

事件回答“什么时候、怎么发生”，不能自动作为当前复测动作。例如“打球落地时崴脚”是受伤经过；只有用户确认现在落地仍会不适时，才能建立当前功能任务。

### 4.2 问题链 `ProblemChain`

```ts
type ProblemChain = {
  id: string;
  primarySite: SymptomSite;
  relatedSites: SymptomSite[];
  currentSymptom?: SymptomFact;
  currentTask?: FunctionalTask;
  userPriority?: number;
  linkedEpisodeIds: string[];
  assessmentState: RegionAssessmentState;
  treatmentState: TreatmentState;
  observations: VersionedObservation[];
  status: "pending" | "active" | "stage-complete" | "follow-up" | "medical-followup";
};
```

大腿、小腿和足部位置可以是独立主诉，也可以只是另一问题链的相关位置。是否建立完整关节流程，由当前症状、功能和检查需要决定，不由位置名称直接决定。

### 4.3 关系假设 `ProblemRelationship`

```ts
type ProblemRelationship = {
  id: string;
  fromProblemId: string;
  toProblemId: string;
  hypothesisType: "shared-event" | "movement-chain" | "load-compensation" | "unknown";
  status:
    | "possible"
    | "functional-gap-found"
    | "immediate-function-supported"
    | "trend-supported"
    | "currently-unsupported";
  supportingEvidenceIds: string[];
  contraryEvidenceIds: string[];
  reviewAfterSessions: number;
};
```

关系状态不使用“已证明导致”。即使多次趋势同步改善，也只能记录为“趋势支持相关”。

### 4.4 每个问题独立保存状态

每条问题链必须独立保存：

- 评估队列和结果；
- 当前处理队列；
- 已处理区域和版本；
- 主诉、活动度、动作质量和训练反馈；
- 当次与跨次完成状态。

总病例只负责调度，不能使用一个全局 `assessmentIndex`、`candidateIndex` 或复测分数代表全部问题。

## 5. 病例调度器

### 5.1 优先顺序

1. 需要优先医学确认的信号；
2. 急性损伤、承重明显受影响或生活功能影响较大；
3. 用户本次最想解决的问题；
4. 会明显影响另一问题评估的功能缺口；
5. 其他独立或长期问题。

用户不知道先处理哪个时，系统给出推荐顺序并允许修改。

### 5.2 一次只展示一个问题链

```text
本次发现 2 个问题

正在处理：右膝下楼疼
稍后处理：右踝旧伤后活动偏小
```

不允许在膝、踝检查之间来回穿插。当前问题完成阶段性评估、处理和复测后，调度器再决定：

- 进入第二问题的快速筛查；
- 进入第二问题的完整流程；
- 将第二问题留到下次；
- 直接进入跨关节训练整合。

### 5.3 相邻关节只做条件性筛查

以近期膝痛和旧踝伤为例，先检查：

- 膝伸直、屈曲和主诉功能；
- 膝局部相关肌肉与控制；
- 踝背屈、外翻控制；
- 必要时观察承重、走路或下台阶的髋膝踝联动。

只有踝筛查发现明确功能缺口，才把踝升级为当前阶段的关联问题。未发现异常时，不展开踝四方向、足趾和全部功能检查。

## 6. 多关节代偿的验证方法

多关节代偿不能沿用“每处理一块肌肉，立即复测主诉；没有减痛就否定”的单关节逻辑。

### 6.1 三个观察窗口

#### 当场可观察

- 相关关节活动范围；
- 动作能否更顺利完成；
- 脚跟、膝轨迹或髋膝踝联动表现；
- 可稳定复现的主诉分数。

主诉没有立即下降，不自动否定该关系。如果踝背屈改善、下台阶更顺，但膝痛不变，记录为“发现功能关联，疼痛关系待趋势观察”。

#### 当天至第二天

- 相同活动量下症状是否更轻或出现得更晚；
- 处理与训练后是否持续加重；
- 关节活动改善能否维持；
- 走路、上下楼或下蹲耐受是否变化。

#### 多次康复趋势

- 上游活动度、力量和稳定是否逐步改善；
- 动作模式是否稳定改善；
- 当前症状区域的代偿性紧张是否逐渐下降；
- 相同负荷下疼痛或不适是否下降；
- 能承受的日常或运动负荷是否提高。

首批可将关系假设设为连续 2～4 次康复的阶段性方向。连续多次功能改善而主诉和生活功能没有趋势变化时，降低该关系优先级，重新检查局部或其他因素。

### 6.2 功能关联与症状关联分开

| 结果 | 系统记录 |
| --- | --- |
| 上游能力改善，主诉立即下降 | 即时功能与症状均支持 |
| 上游能力改善，动作更顺，主诉未变 | 功能支持；症状待趋势观察 |
| 主诉下降，但上游能力未变 | 暂不归因，保留其他局部候选 |
| 多次上游能力和主诉同步改善 | 趋势支持相关 |
| 上游恢复稳定，主诉长期不变 | 当前不支持其为主要贡献因素 |

### 6.3 阶段性方案的组成

复杂代偿通常同时包含：

1. 当前主诉区域的症状与局部能力处理；
2. 上游或下游关节遗留活动、力量和稳定恢复；
3. 髋膝踝协同、步态、下蹲或台阶等功能训练。

不能因为发现上游功能缺口就忽略当前疼痛部位，也不能只恢复关节角度而默认旧动作模式会自行消失。

## 7. AI 主诉收集助手

### 7.1 唯一职责

AI 只负责：

- 理解自然口语、错别字和不完整句子；
- 区分受伤经过、当前症状和恢复目标；
- 提取多个身体位置和左右侧；
- 重建多个发生时间与先后关系；
- 区分当前主要问题、历史问题和其他位置；
- 标出缺失、冲突和不确定信息；
- 根据规则允许的字段，生成最多 2～4 个必要追问；
- 把用户回答更新成结构化候选，交给用户确认。

AI 不负责：

- 判断疾病、组织损伤或医学诊断；
- 判断骨折、韧带或肌腱损伤是否存在；
- 决定安全分流或是否需要影像；
- 确定代偿因果；
- 生成评估队列；
- 选择肌肉松解、关节松动或训练；
- 判断处理是否有效；
- 绕过用户确认写入确定事实。

### 7.2 用户流程

```text
自然描述或语音转文字
→ AI 结构化整理
→ 用户查看简短确认卡
→ 只补问影响路径的缺项
→ 人体图确认关键位置
→ 生成已确认病例事实
→ 规则引擎开始安全确认和评估
```

首屏提示：

> 请说说现在最想解决哪里、什么时候开始、怎么出现的、做什么会不舒服；以前相关位置受过伤也可以一起说。说不全没关系。

AI 整理后的普通用户页面只显示：

```text
现在主要问题
右膝内侧 · 最近两周 · 下楼疼 · 5/10

以前相关问题
右脚踝 · 三个月前崴伤 · 现在勾脚仍偏小

还需要确认
膝盖不舒服是在崴脚以后才出现的吗？
```

用户可以确认、修改、删除或补充。页面不展示 JSON、置信度算法和“代偿假设”等内部术语。

### 7.3 AI 输出合同

AI 必须返回固定 JSON，所有临床字段均为候选：

```json
{
  "primary_problem_candidate": {
    "site": { "side": "right", "region": "knee", "detail": "medial" },
    "symptom": "pain",
    "sensation": null,
    "onset_text": "最近两周",
    "current_task": "下楼",
    "score": 5
  },
  "episode_candidates": [
    {
      "time_text": "三个月前",
      "mechanism": "打球时崴右脚",
      "sites": [{ "side": "right", "region": "ankle" }],
      "reported_findings": ["当时明显肿胀"],
      "reported_imaging": [{ "field": "fracture", "value": "user_reports_not_found" }]
    }
  ],
  "secondary_problem_candidates": [
    {
      "site": { "side": "right", "region": "ankle" },
      "current_finding": "勾脚比左侧小"
    }
  ],
  "relationship_candidates": [
    {
      "from": "right_ankle_history",
      "to": "right_medial_knee_current",
      "status": "possible",
      "basis": ["先后出现", "同侧", "共同涉及下肢负重功能"]
    }
  ],
  "missing_critical_fields": ["右膝不适性质"],
  "conflicts": [],
  "follow_up_questions": [
    "右膝不舒服更像酸、胀、牵扯、刺，还是说不清？"
  ]
}
```

每个候选字段必须带来源状态，实际实现可使用：

- `explicit`：用户原话明确说明；
- `inferred`：AI 根据上下文推断，必须确认；
- `uncertain`：存在多个解释；
- `missing`：未提及；
- `conflict`：前后内容冲突；
- `confirmed`：用户确认后由系统写入，AI 无权直接生成。

### 7.4 追问控制

AI 可以建议追问，但规则层决定是否展示。只有满足以下条件才追问：

- 字段会改变安全确认、主问题选择或评估入口；
- 原文尚未明确获得；
- 用户能够回答；
- 之前没有问过；
- “不知道”仍被接受为有效答案。

多部位场景首轮额外问题通常不超过三个：

1. 现在最想先解决哪个位置或功能？
2. 各问题大概何时出现，后一个是否在旧伤之后出现？
3. 它们是否在走路、楼梯、下蹲等同一种活动中同时受影响？

安全问题继续由固定规则页面询问，不能交给语言模型自由发挥。

### 7.5 人体图的作用

AI 提取的位置只做预选。以下位置仍由用户在图上确认或修改：

- 当前主要不适位置；
- 肿胀或淤青位置；
- 按压不适位置；
- 麻、电或感觉变化范围。

AI 只识别到“腿、膝、脚”等大区域时，不与用户后续点击的细分区域判定为冲突。

### 7.6 失败和降级

- AI 超时或接口失败：保留原文，进入人体图和最少固定问题；
- JSON 校验失败：不写入病例，自动重试一次；仍失败则降级；
- 多种解释：显示一条确认问题，不让 AI 自行选择；
- 没有明确主诉动作：不显示评分，后续检查找到可重复症状时再建立基线；
- 用户全部选择“不知道”：优先当前位置和功能做最少检查，不把未知当阴性。

## 8. AI 与规则引擎的接口边界

```text
用户原话
  ↓
AI Intake Parser
  ↓  只产生候选
Schema Validator
  ↓
User Confirmation
  ↓  形成已确认事实
Case Builder
  ↓
Safety Rules / Case Scheduler / Joint Engines
  ↓
评估、处理、复测、训练
```

只有 `confirmedFacts` 可以进入决策引擎。AI 原始输出和用户确认后的结果分别保存，以便追溯解析错误。

## 9. 页面方案

### 9.1 症状收集

- 一个自然语言输入框，可后续增加语音转文字；
- AI 整理后显示“当前主要问题、以前相关问题、待确认”三块；
- 一次只补一项；
- 选项选择后由用户点击下一步；
- 允许直接修改位置、时间和动作；
- 右侧显示已确认事实，不显示所有后台候选。

### 9.2 多问题流程

- 顶部显示当前问题、待处理问题和阶段性完成问题；
- 中间始终只有一个检查、处理或训练任务；
- 切换问题链时使用简短过渡页；
- 问题链之间共享已经完成的相同动作和处理区域，但观察结果必须带版本，不能跨新处理错误复用。

### 9.3 总结和复诊

总结按问题链展示：

- 本次各问题排查结果；
- 当前主诉区域做过的处理；
- 关联关节发现的功能缺口；
- 当场可确认的变化；
- 需要跨次观察的关系假设；
- 居家训练和下一次复查重点。

复诊不重新询问完整病史，只确认：

- 是否出现新事件或新症状；
- 当前主诉与生活功能趋势；
- 上次保留的局部和关联功能缺口；
- 训练完成情况及当天、第二天反应。

## 10. 重构影响范围

这是中到大型重构，影响较广，但不推翻现有膝踝知识和单处理规则。

### 需要重构

- 症状主诉数据结构；
- AI 候选、用户确认和确定事实的分层；
- 多事件时间线；
- 多问题状态和病例调度；
- 评估、处理和复测状态从全局改为每问题独立；
- 保存恢复和第二、三次康复；
- 统一训练与总结。

### 可以复用

- 膝、踝足现有评估知识；
- 活动方向与肌肉区域关系；
- 处理候选和训练动作库；
- 单个处理单元的去重与复测规则；
- 评分组件、人体位置图和大部分页面组件；
- 线下病例来源和已经审核的知识关系。

## 11. 分阶段实施

### 阶段 A：先抽离单问题运行状态

- 定义 `ProblemChainState` 和版本化观察；
- 把现有膝、踝单关节流程包装成可调用模块；
- 页面暂时仍只运行一个问题；
- 保持现有单关节测试全部通过。

### 阶段 B：建立病例调度器

- 支持最多两个问题链；
- 支持同一事件与不同事件；
- 支持大腿、小腿、足底等非关节主诉位置；
- 一次只调度一个问题，第二问题串行进入。

### 阶段 C：增加跨关节关系与趋势

- 建立 `ProblemRelationship`；
- 增加条件性相邻关节筛查；
- 区分即时功能变化和跨次症状趋势；
- 建立 2～4 次阶段性方案和停止/降级条件。

### 阶段 D：接入 AI 主诉收集

- 先实现固定 JSON 契约和字段校验；
- 再接入模型，仅解析主诉和生成缺项候选；
- 加入确认卡、人体图修正和失败降级；
- 不改变安全与临床决策引擎。

### 阶段 E：复诊与统一训练

- 每次康复独立保存，不覆盖历史；
- 按问题链记录趋势；
- 合并重复训练，生成局部能力、关联关节能力和多关节功能训练；
- 用真实多关节病例审核路径。

## 12. 首批验收场景

1. 同一次崴脚导致踝痛和膝部直接撞伤，生成两条问题链。
2. 下楼膝内侧痛并描述大腿外侧紧，只生成一条主诉链和一个相关区域。
3. 旧踝伤后出现近期同侧膝痛，建立待验证关系和踝短筛查。
4. 踝背屈当场改善、膝痛未变，不否定关联，进入趋势观察。
5. 连续多次踝功能和膝功能同步改善，关系更新为趋势支持。
6. 踝功能恢复稳定但膝痛长期不变，降低踝关系优先级并重新排查膝局部因素。
7. 多部位但不同侧、不同功能且无关联证据，保持独立，不强行建立代偿。
8. 用户只描述受伤过程，AI 不把发生动作当成当前复测动作。
9. AI 未识别疼痛性质或具体位置，显示待确认，不预设答案。
10. AI 接口失败后仍能通过人体图和最少固定问题完成症状收集。
11. 新症状进入后不继承旧问题的分数、队列和处理结果。
12. 第二、三次康复使用跨次趋势，不因一次没有即时减痛就删除长期处理方向。

## 13. 本方案的最终边界

AI 解决的是“用户怎样把复杂病史说出来，系统怎样少问几题并整理清楚”。

病例调度器解决的是“多个问题先做哪个、何时筛查第二关节、怎样保存彼此独立的状态”。

关系与趋势层解决的是“复杂代偿不能只靠一次即时复测判断”。

三者不能互相替代。尤其不能因为接入 AI，就让模型直接决定代偿因果、检查内容或康复方案。
