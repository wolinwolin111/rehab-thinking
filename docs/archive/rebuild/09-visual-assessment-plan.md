# 09 视觉辅助评估方案

> 当前状态：只做方案，不接入当前 Demo  
> 首批范围：膝关节、踝足  
> 目标：减少用户看不懂、不会判断和选项过多的问题
> 产品定位：视觉辅助记录，不做影像学诊断或组织结构判断

## 1. 视觉能力放在什么位置

视觉分析是“检查结果的辅助记录工具”，不是新的诊断入口。

它可以帮助回答：

- 动作有没有完成；
- 左右活动范围相差多少；
- 某个动作在哪一段出现明显异常；
- 是否存在明显晃动、偏移、提前抬脚跟或借力；
- 处理前后同一动作的范围和动作表现有没有变化。

它不能从画面直接判断：

- 用户哪里疼、是什么感觉、疼痛几分；
- 肌肉是否紧张、按压哪里痛；
- 被动活动范围和关节末端感觉；
- 韧带、肌腱、半月板或骨性结构是否损伤；
- 某块肌肉的真实力量；
- 肿胀、淤青和皮肤温度是否已经达到医学判断标准。

因此，视觉结果只能替代“用户看动作后自行判断”的部分，不能替代症状问答、触诊、专业被动检查和必要影像。

## 2. 首批适合视觉计算的检查

### 膝关节

| 检查动作 | 视觉可计算内容 | 用户仍需回答 |
|---|---|---|
| 仰卧把膝盖绷直 | 左右膝伸直角度、能否保持、明显抖动 | 是否出现不适、位置、感觉、分数 |
| 仰卧脚跟滑向臀部 | 左右屈膝角度、脚跟移动距离 | 是否出现不适、位置、感觉、分数 |
| 下蹲 | 下蹲深度、骨盆或躯干可见偏移、膝盖明显内外偏、躯干借力 | 哪一段不适、位置、感觉、分数 |
| 下台阶 | 下降深度、膝盖轨迹、骨盆和躯干偏移、动作速度 | 哪一段不适、位置、感觉、分数 |
| 单脚站立 | 保持时间、身体晃动、骨盆明显偏移 | 是否不稳或不适 |
| 踮脚 | 次数、脚跟抬起高度、左右差和节奏 | 小腿或膝部是否不适 |

### 踝足

| 检查动作 | 视觉可计算内容 | 用户仍需回答 |
|---|---|---|
| 脚背向上勾、向下压 | 小腿与足部的相对角度、左右差 | 是否不适、具体位置、感觉、分数 |
| 膝盖碰墙 | 踝背屈角度、脚跟是否明显抬起、左右差；有标尺时再算距离 | 踝前卡痛或小腿牵扯的位置和分数 |
| 双脚或单脚踮脚 | 次数、抬起高度、速度、左右偏移 | 跟腱、小腿或踝足是否不适 |
| 单脚站立 | 保持时间、晃动幅度、扶持次数 | 是否感觉不稳或疼痛 |
| 下蹲 | 脚跟是否提前抬起、膝向前范围、左右偏移 | 踝足不适位置和感觉 |
| 短距离走路 | 步长、左右支撑时间、明显跛行、身体偏移 | 哪一步不适、是否敢承重 |

脚掌内翻、外翻和足弓细微变化对摄像机角度、遮挡和足部关键点精度要求较高，第一版仍以引导动作加用户选择为主，不把视觉估计当成确定结果。

二维画面看到的身体偏移不等于真实足底压力或关节受力；没有标尺或已知尺寸参照时，也不能把像素距离直接写成厘米。页面必须把这类结果表述为“画面中向左偏得更多”“这次比上次更接近”，不能写成“左腿承重不足”等未经测量的结论。

## 3. 推荐的技术路线

### 首选：设备端姿态识别，后台保存计算结果

1. 网页申请相机权限；
2. 用户按屏幕轮廓摆好手机和身体；
3. 浏览器在本机运行姿态模型；
4. 只把关节关键点、角度、次数、左右差、置信度和用户反馈保存到后台；
5. 原始视频默认不上传、不长期保存。

这里的“后台计算”拆成两层：姿态关键点和基础角度优先在用户设备上完成；业务后台负责保存结构化结果、前后比较、模型版本、审计记录和决策映射。如果低性能设备无法稳定运行，再启用可选的服务端分析，但不能一开始就默认上传患者视频。

首批建议使用 MediaPipe Pose Landmarker。官方 Web 任务可以处理图像和视频，输出 33 个身体关键点、可见度、图像坐标与三维世界坐标，适合先做膝、髋、踝的基础姿态计算。视频推理需要放进 Web Worker，避免阻塞页面。[Google MediaPipe Pose Landmarker for Web](https://developers.google.com/edge/mediapipe/solutions/vision/pose_landmarker/web_js)

MoveNet 可作为性能或兼容性备选；官方提供 Lightning 和 Thunder 两个版本，并输出 17 个关键点。[TensorFlow MoveNet](https://www.tensorflow.org/hub/tutorials/movenet)

相机访问必须由用户主动授权，并且正式环境需要 HTTPS；浏览器也会持续提示相机正在使用。[MDN getUserMedia](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia)

如果后续建设原生 iOS 客户端，可以评估 Apple Vision 的 2D/3D 人体姿态能力；它同样提供关节点及置信度，但不能与 Web 版结果直接混用，必须按模型和平台分别验证。[Apple Vision 人体姿态识别](https://developer.apple.com/documentation/vision/detecting-human-body-poses-in-images)

### 为什么不建议第一版直接调用通用视觉大模型

通用视觉大模型适合解释一张图或粗略描述动作，但不适合作为连续视频的稳定角度计、计数器和前后复测工具。第一版需要的是相同条件下可重复计算，而不是每次生成一段不同的自然语言判断。

后续可以让视觉大模型把计算结果翻译成用户能看懂的话，或在低置信度和遮挡明显时提示重新拍摄。它不直接输出“某肌肉紧张”“某结构损伤”或处理方案。

## 4. 用户实际看到的流程

```text
现在检查：下台阶
→ 选择“相机辅助”或“自己记录”
→ 屏幕提示手机摆放位置和全身入镜范围
→ 先做一次试拍，系统确认身体和台阶都看得清
→ 正式完成3次
→ 系统显示：右侧下降较浅、膝盖向内偏较明显
→ 用户在局部图上点击不适位置
→ 用户选择感觉和0～10分
→ 保存为一条可复测记录
```

视觉结果不能静默写入。用户至少要看到并确认：

- 系统识别的是哪一侧、哪一个动作；
- 哪些结果可信；
- 哪些结果因为遮挡或角度不够而无法判断；
- 不适位置、感觉和分数仍由用户填写。

### 页面只保留四个短步骤

1. **摆好手机**：显示一个机位示意图和人物轮廓；
2. **试做一次**：系统只检查是否入镜、是否遮挡和视角是否合适；
3. **正式完成动作**：界面只显示动作名称、次数和停止按钮；
4. **确认结果**：显示系统观察和症状问答，用户可以确认、修改或选择“看不清”。

视觉入口必须是可选项。用户不愿拍摄、没有支架或系统反复识别失败时，立即回到当前手动问答，不增加新的必答题。

## 5. 每个动作的固定拍摄模板

同一项检查不能让用户自己猜机位。每个 `assessmentId` 绑定一个固定模板：

| 动作 | 首选视角 | 画面要求 | 正式记录 |
|---|---|---|---|
| 膝伸直 | 侧面，镜头约与膝同高 | 髋、膝、踝完整入镜，双腿不互相遮挡 | 两侧各保持 2～3 秒 |
| 膝屈曲 | 侧面，镜头约与膝同高 | 大腿、小腿和足跟完整入镜 | 两侧各做 2 次 |
| 下蹲 | 正面；需要角度时补侧面 | 双脚、膝、骨盆和躯干完整入镜 | 连续做 3 次 |
| 下台阶 | 正面或前侧 30～45 度 | 台阶、支撑脚、膝和骨盆完整入镜 | 同一侧做 3 次 |
| 膝盖碰墙 | 侧面，镜头约与踝同高 | 脚跟、踝、膝和墙面完整入镜 | 两侧各做 2 次 |
| 踮脚 | 后面 | 双侧小腿、脚跟和前脚掌完整入镜 | 做到目标次数或主动停止 |
| 单脚站立 | 正面 | 全身或至少骨盆至足部完整入镜 | 最长记录 20 秒 |
| 短距离走路 | 正面来回或侧面 | 至少能看到连续 3～4 步 | 往返各一次 |

前后复测必须调用同一个模板，并尽量复用同一手机位置、视角、鞋袜状态、台阶高度和扶持条件。系统比较的是“同一个人在相近条件下的变化”，不是把一次随意拍摄与统一标准硬比较。

## 6. 后台计算流程

```text
评估项目
→ 调用对应拍摄模板
→ 画面质量检查
→ 姿态关键点识别
→ 轨迹平滑与动作分段
→ 计算角度、距离、次数和偏移
→ 置信度判断
→ 用户确认
→ 写入现有评估记录
```

画面质量检查至少包括：

- 目标身体部位是否完整入镜；
- 关键点是否被衣物、家具或另一条腿遮挡；
- 是否只有一名被检查者；
- 光线、清晰度和镜头晃动是否可用；
- 身体朝向是否符合模板；
- 台阶、墙面或地面等任务参照物是否可见。

每次视觉检查保存：

```text
动作ID
拍摄视角
关键点置信度
有效重复次数
左右关节角度或距离
动作起始、中段和末段指标
明显偏移或晃动指标
是否达到质量门槛
用户确认的不适位置、感觉和分数
处理前或处理后
```

判断顺序：

1. 先做画面质量检查；
2. 质量不足时只提示重新摆位，不生成异常；
3. 优先与健侧或本人上一次结果比较；
4. 没有健侧可比时，再使用动作专用参考范围；
5. 视觉指标只生成“范围偏小、左右差明显、动作偏移明显”等观察，不生成组织诊断；
6. 用户报告的不适与视觉异常一起进入现有决策引擎。

单摄像机画面会受到透视、镜头畸变和身体未正对拍摄平面的影响，因此第一版优先做左右差、本人前后差和明显异常分组，不承诺所有动作都达到临床量角器精度。相机标定能够修正部分镜头畸变，但无法消除用户机位和动作平面不一致造成的误差。[OpenCV 相机标定说明](https://docs.opencv.org/4.x/dc/dbb/tutorial_py_calibration.html)

## 7. 怎样接入现有评估与处理流程

视觉层输出的字段与手动评估字段保持一致：

- `rangeStatus`：接近健侧 / 小于健侧 / 无法判断；
- `controlStatus`：基本稳定 / 明显晃动或借力 / 无法判断；
- `completionStatus`：完成 / 因不适未完成 / 拍摄失败；
- `metricBefore` 与 `metricAfter`：处理前后的角度、距离、次数或晃动指标；
- `confidence`：高 / 中 / 低；
- `userSymptom`：位置、感觉、0～10分、是否为平时熟悉症状。

现有 `AssessmentRecord` 保留为最终记录，视觉分析只增加一份证据，不直接覆盖用户答案：

```ts
type VisualAssessmentEvidence = {
  assessmentId: string;
  captureTemplateId: string;
  modelName: string;
  modelVersion: string;
  view: "front" | "side" | "rear" | "oblique";
  phase: "before" | "after" | "followup";
  quality: {
    passed: boolean;
    reasons: string[];
  };
  metrics: Array<{
    id: string;
    value: number;
    unit: "degree" | "second" | "count" | "ratio";
    comparison: "contralateral" | "previous" | "task-reference";
    confidence: "high" | "medium" | "low";
  }>;
  observations: Array<{
    id: string;
    label: string;
    confidence: "high" | "medium" | "low";
  }>;
  status: "accepted" | "edited" | "recapture" | "manual-only";
  confirmedByUser: boolean;
};
```

写回规则：

- 高置信度：预填“接近另一侧 / 小于另一侧”等结果，等待用户确认；
- 中置信度：展示两侧或前后画面对比，让用户选择；
- 低置信度：不生成正常或异常结论，回到原来的手动选项；
- 用户修改后，以用户确认结果作为流程输入，同时保留视觉原值供质量复盘；
- 疼痛位置、性质、分数和熟悉症状永远不由视觉自动填写；
- “不知道”仍然是有效结果，不能因为缺失就直接结束整个问题。

现有决策引擎只使用高、中置信度的观察。低置信度等同“暂未判断”，不能当作正常，也不能因此取消后续全部处理。

处理后的复测必须使用同一动作、同一视角和相近机位。系统同时比较：

- 主诉分数是否下降；
- 活动范围是否更接近健侧；
- 动作偏移是否减少。

三项结果分别保存，不能因为疼痛下降就自动把活动范围标记完成。

### 与知识库和处理路线的关系

视觉层不新增一套治疗逻辑。用户确认后的结果继续转换为现有 `PilotFindingInput`，由膝踝知识关系决定下一项检查、处理和训练：

```text
视觉观察：右膝伸直比左侧少
+ 用户反馈：伸直到末端出现熟悉的膝后牵扯感，4分
→ 现有发现：knee-extension 受限并复现主诉
→ 进入原有候选处理排序
→ 处理后用同一模板复测角度，同时重新记录症状分数
```

这样做能保证视觉 AI 真正减少用户判断难度，但不会绕过此前已经完成的“资料来源—评估发现—候选处理—复测—训练”闭环。

视觉能力也不能用来掩盖评估流程本身的问题。每个动作仍需满足以下规则：

- 用户只看到一句“现在做什么”和一句“做的时候留意什么”；
- 同一个动作在主诉复现、活动度和功能检查中只做一次，结果同时写入相关字段；
- 动作没有不适时不追问位置、性质和分数；
- 动作出现不适时才打开局部图、感觉和分数记录；
- “不知道”和“拍摄失败”只表示当前证据缺失，不等于正常，也不直接取消后续所有流程；
- 视觉发现必须确实改变评估记录或复测数据，否则不展示给用户。

## 8. 分阶段落地

### 视觉阶段 0：只做引导和回放

- 建立固定机位模板；
- 录制后允许慢放和前后并排；
- 不生成自动结论；
- 用真实用户视频验证动作说明是否看得懂。

### 视觉阶段 1：先验证四个动作

- 膝伸直；
- 膝屈曲；
- 下蹲；
- 膝盖碰墙。

这四项机位相对容易控制，也能直接帮助当前膝踝活动度和功能检查。

### 视觉阶段 2：加入功能动作

- 下台阶；
- 单脚站立；
- 双脚和单脚踮脚；
- 短距离走路。

### 视觉阶段 3：再考虑更复杂动作

- 跑跳落地；
- 变向；
- 多平面动作；
- 足弓和内外翻的更细识别。

只有当前四个动作与人工记录的一致性通过验证后，才进入下一阶段。

## 9. 验证与放行标准

每个动作至少验证：

- 同一人连续拍三次，结果是否稳定；
- 与康复师人工判断是否一致；
- 左右侧是否会识别反；
- 手机距离、角度、衣物和光线改变后误差多大；
- 处理前后的小变化能否稳定识别；
- 低置信度时是否会正确提示“无法判断”，而不是给出错误结论。

首批内部目标不是追求医学级量角器精度，而是先可靠区分：接近健侧、明显偏小、明显偏大或无法判断。

每个动作单独建立验证集，不能用“膝伸直准确”推定“下台阶也准确”。验证记录至少包含不同手机、机位偏差、衣物、光线、身材、左右侧和真实功能水平。人工参照由康复师按统一模板记录；角度任务再与量角器或逐帧人工标注比较。

首批统计至少包括：

- 角度或距离的平均绝对误差；
- 同一人重复拍摄的一致性；
- “接近健侧 / 明显偏小 / 无法判断”的一致率；
- 明显代偿识别的精确率和召回率；
- 需要重拍或最终退回人工的比例；
- 左右侧识别错误率；
- 处理前后变化方向是否与康复师判断一致。

具体放行阈值不能在没有样本时拍脑袋设定。先收集内部样本并报告误差分布，再由康复师确定哪些指标可以进入决策、哪些只能展示给用户参考。已有研究说明单摄像机姿态估计在部分髋膝主动活动范围测量中有潜力，但准确度会随任务变化，因此必须逐动作验证。[髋膝主动活动范围验证研究（PubMed）](https://pubmed.ncbi.nlm.nih.gov/39897097/)

## 10. 隐私、成本与运行方式

- 首版优先在设备端计算，原始视频默认不上传；
- 后台只保存用户确认后的结构化指标、模型版本和质量信息；
- 如需上传视频用于质量改进，必须单独说明用途、保存时间和删除方式，并取得明确同意；
- 画面可在本地裁切到下肢或做人脸模糊，减少身份信息；
- 模型升级后保留版本号，旧结果不静默重算；
- 第一版不需要付费视觉大模型接口，主要成本在动作模板、数据标注、康复师复核和真实设备验证；
- 通用视觉大模型以后只用于拍摄指导或把结构化结果转成通俗提示，不负责角度计算、组织判断或诊断。

## 11. 开发前必须准备的内容

1. 为四个首批动作写完机位、动作、停止条件和失败示例；
2. 定义每个动作所需关键点和计算公式；
3. 定义质量检查、置信度和手动回退规则；
4. 建立康复师人工标注表；
5. 收集多设备、多身材、多衣物条件的内部样本；
6. 先完成离线计算原型，再决定是否把相机入口放入产品；
7. 只有验证通过的指标才能写入决策引擎。

## 12. 当前结论

视觉辅助值得加入，但产品顺序应保持不变：先让膝踝手动流程在真实用户中跑顺，再用视觉能力减少“用户不会判断”的步骤。第一版不需要付费视觉大模型接口；可以先用设备端姿态模型完成低推理成本原型。真正需要投入的是动作机位设计、指标计算、质量门槛、人工标注和逐动作验证，而不是模型调用本身。
