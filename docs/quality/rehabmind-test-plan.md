# RehabMind 最新测试计划

更新时间：2026-08-22

## 1. 文档目的

本文件统一记录 RehabMind 当前阶段的测试原则、测试分层、真实场景覆盖方法、执行门槛和发布条件。

本项目不使用 AI 做康复决策。康复规则由代码中的明确规则、检查证据、权限和安全条件决定。本测试计划也不验证 AI 输出，而是验证：

- 页面是否正确收集用户输入；
- 决策结果是否正确连接到后续检查、处理、复测和训练；
- 不同选项组合是否进入正确的用户出口；
- 保存、恢复、权限和部署是否可靠；
- 页面是否会跳步、漏项、重复、静默结束或错误继续。

本文件是测试执行计划，不新增产品规则。具体规则仍以[产品规范](./rehabmind-complete-product-design.md)、[决策引擎规范](./rehab-decision-framework.md)、[膝踝首发知识库](./knee-ankle-pilot-knowledge.md)和[首发场景验收](./pilot-scenario-coverage.md)为准。

## 当前执行口径（2026-08-22）

本轮按项目负责人的决定执行：不再把真实浏览器自动化作为内部逻辑的常规测试手段，也不把 Playwright 运行时间或浏览器截图作为默认质量门禁。浏览器脚本和既有产物保留为历史证据及必要时的人工验收参考，不删除、不重新运行、不计入本轮内部逻辑覆盖率。

本轮默认门禁调整为：决策规则、状态转换、完整流程轨迹、组合不变量、错误注入、D1/API 集成和人工界面验收。后文仍保留的 L3、Playwright、浏览器覆盖章节属于历史方案或可选发布验收，和本节冲突时以本节为准。

内部流程测试必须调用正式生产逻辑，不能建立一套测试专用决策模型。若生产逻辑仍与页面编排耦合，则采用小范围提取、特征测试、定向回归的方式逐段降低耦合，不进行一次性大重构。

## 2. 当前范围

首发测试范围：

- 大腿、膝、小腿和踝足入口；
- 普通自助、康复思路模式·给自己、康复思路模式·给别人；
- 首次康复和后续康复；
- 症状收集、安全确认、评估、处理、复测、训练、总结；
- 本地 D1、Cloudflare 预览环境和正式试用环境；
- 桌面 Edge 为当前主要浏览器，移动端做关键页面抽查。

暂不作为当前试用验收范围：

- 案例学习入口和学习解释开关（当前页面入口尚未完成）；
- 多关节联合处理；
- 视觉 AI、语言模型决策和正式视频系统；
- 复杂账号体系和多人协作。

## 3. 核心原则

### 3.1 用户路径优先

源码中存在规则、文字或组件，不等于流程正确。内部逻辑结论必须有正式函数调用、状态轨迹和设计规则依据；页面标题、按钮和视觉布局属于人工界面验收，不作为本轮内部逻辑自动测试的前置条件。

### 3.2 代码测试和浏览器测试分工

| 测试 | 主要回答的问题 | 不能单独证明的内容 |
| --- | --- | --- |
| 代码组合测试 | 这组输入交给规则后应该返回什么 | 页面是否真的展示并推进到这个结果 |
| 流程状态测试 | 结果接入工作流后阶段和队列如何变化 | 用户是否能通过真实按钮触发该状态 |
| 内部流程轨迹测试 | 正式生产逻辑在连续事件下如何变化 | 真实页面视觉和浏览器兼容性 |
| 浏览器场景测试（可选） | 用户实际看到什么、能做什么、不能做什么 | 所有隐藏组合是否都被穷举 |
| 持久化测试 | 数据是否正确保存、恢复、隔离和追溯 | 页面是否正确理解业务结果 |
| 人工验收 | 用户和专业人员是否理解页面 | 所有规则组合是否没有回归 |

代码组合和流程轨迹测试负责内部规则、分支和状态组合；浏览器只在需要人工确认页面接线、兼容性或视觉时使用。不能用浏览器终点证明内部规则，也不能用代码覆盖率证明页面体验。

### 3.3 历史通过不等于当前自动覆盖

历史人工走读可以保留为证据，但只有当前可重复执行、带有明确页面断言的脚本，才能标记为当前浏览器通过。

### 3.4 测试架构的高内聚低耦合约束

此前讨论中确定的高内聚低耦合不仅适用于业务代码，也适用于测试代码：

- 决策规则测试直接调用独立的纯核心模块，不通过大页面组件或字符串匹配间接证明规则；
- 流程状态测试只验证阶段、队列、复测资格和版本失效，不重复实现决策规则；
- 浏览器脚本只通过用户可见文本、语义角色和稳定的测试标识操作，不读取 React 内部状态，也不注入内部状态绕过页面；
- 浏览器公共操作、教程关闭、错误收集和证据保存集中在共享 helper；每条业务场景只保留自己的输入、点击顺序和断言；
- 持久化测试通过服务/API 边界验证保存、恢复、冲突和权限，D1 仓储测试只负责数据库约束，不把数据库实现细节扩散到页面脚本；
- 每个场景只有一个 `scenarioId`、一份固定夹具和一个证据目录，规则测试、浏览器测试和部署测试通过该 ID 关联，禁止复制一套相似但含义不清的走读脚本；
- 通用“找第一个可点击项”的走读器只能探索页面或发现死路，不能作为覆盖率或发布通过依据。

因此，测试数量增加不等于覆盖率增加。新增场景必须先说明它验证的边界，再选择最小的测试层；同一条业务规则不在多个层重复实现。

## 4. 测试分层

| 层级 | 内容 | 运行时机 | 通过标准 |
| --- | --- | --- | --- |
| L0 工程质量 | typecheck、lint、build、首页启动 | 提交前、部署前 | 项目可编译、可启动、无静态错误 |
| L1 决策规则 | 411 条规则测试、临床组合矩阵、权限组合、结果不变量 | 修改规则时、发布前 | 所有合法组合有明确处理、训练、复测或停止出口 |
| L2 流程状态 | 阶段切换、队列重排、复测资格、版本失效、训练门槛 | 修改流程状态时 | 不跳步、不重复、不静默结束、不跨版本继续 |
| L3 内部流程轨迹 | 正式编排函数、事件序列、状态与决策依据 | 修改流程时 | 每个关键转换有可解释的前后状态 |
| L4 浏览器与人工界面 | 页面、视觉、兼容性和用户理解 | 重要版本或界面修改时 | 人工验收或明确的可选浏览器证据 |
| L5 数据与部署 | 本地 D1、预览 Worker/D1、保存、恢复、隔离、冲突、反馈、删除 | 预览部署前、正式试用前 | 用户数据可追溯，案例不串线，失败有可理解出口 |

本地运行上述测试不会调用模型，也不会按测试条数消耗模型 Token。通过 Codex 发起和分析命令会占用对话上下文；浏览器、Node、D1 本地运行本身只消耗本机时间和资源。预览环境另外消耗 Worker 请求和 D1 读写额度。

## 5. L1/L2 代码测试内容

### 5.1 决策规则

覆盖以下输入和结果：

- 正常、活动受限、活动过大；
- 疼痛无法完成、没力、害怕加重、不会做；
- 未知、暂不判断、暂不检查、未测试；
- 肿胀、按压痛、麻电和新无力；
- 单侧、双侧和优先侧冲突；
- 自助、给自己、给别人和能力组合；
- 急性、亚急性、慢性和影像门控；
- 处理有效、无变化、部分改善、加重；
- 训练完成、训练后不适、停止后回落和再次加重。

代码层应断言：

- 处理、复测和训练目标有证据来源；
- 同一物理动作和处理区域去重；
- 未知不能变成正常；
- 力量/控制问题进入训练；
- 肿胀等时间性目标不能要求即时普通复测；
- 不同动作不能复用错误结果；
- 旧版本计划在上游修改后失效；
- 所有安全、待确认和专业评估出口明确。

### 5.2 流程状态

至少覆盖：

- 选择答案不自动跳题；
- 缺字段时下一步禁用并显示待补内容；
- 处理后必须进入合适复测或明确继续出口；
- 训练反馈未完成不能结束；
- 动态队列插入新候选后不跳过；
- 返回修改只清除受影响的下游数据；
- 保存恢复后模式、权限、阶段、版本和未完成字段一致；
- 同一次康复不会因为重复保存或重新打开增加次数。

## 6. L3 真实浏览器覆盖方法

### 6.1 每条场景必须具备的内容

每个场景使用固定 `scenarioId`，记录：

- 初始输入和操作模式；
- 明确的点击顺序；
- 每个关键页面标题；
- 应出现的内容；
- 禁止出现的内容；
- 选项、按钮和滑条状态；
- 处理、复测、训练和总结结果；
- 保存/恢复结果；
- 浏览器 error 日志；
- 截图、DOM 快照和失败位置。

禁止使用“找到第一个可点击按钮并一直点击到总结”的脚本作为主要验收。通用走读器只能用于探索，不能作为关键场景的唯一证据。

### 6.2 浏览器覆盖率定义

浏览器覆盖率不使用代码行覆盖率，而使用以下业务指标：

1. 覆盖矩阵每条 P0 规则是否绑定当前脚本；
2. 每类用户选项是否至少有一条真实页面路径；
3. 每个高风险条件是否有正向和反向场景；
4. 每个关键阶段是否同时覆盖正常、异常、未知和停止出口；
5. 关键组合是否覆盖，而不是只覆盖单个选项；
6. 每条场景是否有应出现和禁止出现两类断言；
7. 当前脚本是否连续运行三次稳定通过。

完整矩阵见[真实场景覆盖矩阵](./real-browser-coverage-matrix.md)。

### 6.2.1 当前覆盖率基线

当前基线分开记录“组合已经被代码执行”和“用户路径已经被浏览器执行”，不把两者相加：

| 指标 | 当前口径 | 是否等于浏览器覆盖 |
| --- | --- | --- |
| 权限组合 | 384 组（2 种模式 × 3 种操作对象 × 64 种能力组合） | 否，属于规则/流程层 |
| 临床组合 | 1728 组 | 否，属于规则层 |
| 随机状态序列 | 1000 条有种子序列 | 否，属于流程状态层 |
| 旧版完整页面路径 | 历史记录 21/24 | 否，只能作为历史证据 |
| 当前真实浏览器闭环 | 当前固定脚本已实际执行的膝、踝、髌骨三类路径 | 是，但只覆盖这三条路径 |
| 当前自动化代码测试 | 最新基线 494 条 | 否，不能替代页面操作 |

发布记录必须同时填写组合层、状态层和浏览器层的结果。不能用“494 条测试通过”或“1728 组通过”填充浏览器覆盖率。

### 6.3 组合场景选取

浏览器不穷举全部笛卡尔积，而采用“单选项覆盖 + 关键成对组合 + 高风险三元组合”：

| 组合维度 | 必测关系 |
| --- | --- |
| 模式 × 权限 | 自助/给自己/给别人，能力有无 |
| 急性状态 × 影像 | 安全通过、高风险停止、无影像禁入 |
| 肿胀 × 后续队列 | 肿胀完成后继续，不直接结束 |
| AROM/PROM × 专业能力 | 关节入口开放和关闭 |
| 功能结果 × 复测 | 正常、无法完成、不同动作、同一动作 |
| 处理结果 × 队列 | 有效、无变化、部分改善、加重 |
| 训练反馈 × 版本 | 未反馈、完成、加重、一次退阶 |
| 保存状态 × 网络 | 正常、超时、冲突、刷新中断 |

### 6.4 场景族

真实浏览器场景不围绕一个已知 Bug 设计，而围绕容易失效的机制设计：

- 输入冲突：位置、动作、肿胀、按压痛和麻电组合；
- 证据组合：活动、功能、疼痛、力量、控制和未知的混合；
- 队列变化：处理有效、无效、部分改善和新候选插入；
- 权限变化：模式、操作对象和能力切换；
- 时间变化：后续康复、次日反应、新症状和旧版本；
- 异常操作：返回、快速点击、重复保存、刷新和断网。

已知的功能动作无法完成问题只保留为一条回归场景，不作为浏览器覆盖设计的中心。

### 6.5 发散场景库

以下场景不是围绕已经发现的某一个 Bug，而是围绕容易让决策链失真的组合关系建立。它们必须进入覆盖矩阵，不能只停留在头脑风暴清单。

#### 输入和症状组合

- `MIX-01`：只有疼痛位置，没有明确动作；不能因为位置词生成整套处理。
- `MIX-02`：有肿胀但没有疼痛；应进入时间性观察或低刺激出口，不生成疼痛处理。
- `MIX-03`：疼痛、肿胀和麻电同时存在；安全/专业确认优先，不能被普通肌肉处理覆盖。
- `MIX-04`：填写多个症状位置，但只有一个位置在评估中异常；其他位置不能自动生成处理。
- `MIX-05`：用户原话与后续选择互相矛盾；修改后的选择应使受影响的下游计划失效。
- `MIX-06`：主动活动接近健侧，但明确功能动作仍疼痛；活动正常不能清除功能问题。
- `MIX-07`：活动范围受限但没有明显疼痛；应区分活动度问题和疼痛问题。
- `MIX-08`：活动接近健侧但力量或控制偏弱；应进入训练而不是手法处理。
- `MIX-09`：功能动作正常但局部按压仍有不适；主诉改善不能清除后续观察问题。
- `MIX-10`：双侧主诉中用户优先侧与评估更差侧不一致；只能提醒，不能静默替换优先侧。
- `MIX-11`：正常、未知和异常结果同时存在；各类结果必须分别进入正常、待确认和处理/训练出口。

#### 处理队列组合

- `QUEUE-01`：第一项处理有效，第二项问题仍未改善；不能因为主诉改善直接结束。
- `QUEUE-02`：第一项处理无变化但没有加重；应进入下一候选或明确观察，不得伪装成成功。
- `QUEUE-03`：活动范围改善但疼痛没有改善；保留两种趋势，不能只显示一个总结果。
- `QUEUE-04`：疼痛改善但活动表现变差；停止当前处理并进入聚焦复查。
- `QUEUE-05`：同一处理目标由多个评估项目触发；只显示一个处理单元，但保留所有相关复测关系。
- `QUEUE-06`：复测后新候选插入旧队列；新开放的同一问题候选必须优先执行。
- `QUEUE-07`：即时处理都完成但仍有后续观察问题；进入观察或训练，不显示空白结束页。

#### 权限和时间组合

- `PERM-01`：自助模式出现专业能力字段；字段不能改变自助权限。
- `PERM-02`：给自己检查时尝试选择被动活动或关节处理；必须隐藏或阻止。
- `PERM-03`：给别人检查但只有触诊能力；不能因为专业模式自动开放PROM或关节处理。
- `PERM-04`：先选择关节处理，再取消被动活动能力；已选关节处理必须清除，旧计划失效。
- `TIME-01`：第一次保存未完成，第二次恢复继续；不能回到默认模式或默认阶段。
- `TIME-02`：第二次康复沿用上次结束分数和方向状态；不能重新使用首诊分数。
- `TIME-03`：第二次康复出现新症状；新问题不能覆盖旧问题。
- `TIME-04`：康复结束后当天或次日出现反应；应追加观察，不增加康复次数。
- `TIME-05`：连续两次训练后加重；退阶不能无限循环，必要时进入专业评估。

#### 用户异常操作组合

- `OPS-01`：快速连续点击“下一步”；不能重复提交或跨过当前字段。
- `OPS-02`：选择后立即返回并修改；下游旧答案和旧计划按依赖关系失效。
- `OPS-03`：保存时刷新；应保留最近一次成功快照，不生成半条进度。
- `OPS-04`：两个窗口同时保存；旧修订号不能覆盖新快照，应显示冲突。
- `OPS-05`：断网后继续填写并恢复；页面不能假装已经同步服务器。

## 7. A/B 缺口处理

覆盖矩阵中的 A/B 采用不同处理方式：

### A：完全没有真实浏览器证据

优先新建脚本，当前包括：

- 明确主诉动作正常后的递进；
- 不同动作不能复用复测，同一动作可以复用的正向对照；
- 麻电、感觉变化或新无力停止；
- 多案例隔离；
- 网络失败和刷新中断；
- 删除、失效链接和管理员保护；
- 预览 D1、版本标识和环境隔离；
- 教程完整流程；
- 跨浏览器冒烟。

### B：历史走过但当前不可重复

将历史走读改成当前固定脚本，优先包括：

- 权限正反路径；
- 急性高风险和高分疼痛停止；
- 力量偏弱、未知、无法完成；
- 髌骨单方向受限；
- 关节入口开放和关闭；
- 肿胀处理后继续队列；
- 处理后加重；
- 训练反馈门槛和训练退阶；
- 自动保存、修订冲突、反馈绑定和后台读取。

历史记录只有在当前脚本补齐后，才能从“覆盖·历史浏览器”改为“覆盖·本轮浏览器”。

### A/B 场景筛选规则

发散场景库不是单独最后执行的一批测试，而是 A、B 两组的补充来源。每次开始一批浏览器测试前，先从库中筛选高风险且尚未有当前页面证据的场景：

- 没有真实页面证据的发散场景进入 A 组；
- 只有历史人工记录或规则/服务层证据的进入 B 组；
- 已有当前固定脚本和关键断言的保留为回归，不重复制造新脚本；
- 先执行 P0，再执行 P1，P2 作为人工产品验收或后续版本任务；
- 每个入选场景必须绑定 `scenarioId`、固定夹具、预期出口和覆盖矩阵行。

当前优先从以下机制中筛选：输入与症状冲突、处理队列重排、权限切换、后续康复时间变化、返回/快速点击/断网等异常操作。筛选结果在进入 A/B 脚本前写入矩阵，执行后立即更新状态和证据。

本轮已经完成首批筛选，具体的 P0、P1、`scenarioId`、固定夹具和预期/禁止内容见[真实场景覆盖矩阵的首批执行清单](./real-browser-coverage-matrix.md#首批执行清单)。

## 8. L4 本地与预览环境验收

### 本地 D1

- 空数据库迁移和重复迁移；
- 创建案例、匿名编号和访问凭据；
- 快照修订号递增；
- 事件幂等和事件顺序；
- 旧修订冲突；
- 两个案例交叉读写隔离；
- 反馈绑定案例、具体目标记录/阶段或未定位状态，并保留提交来源位置；
- 损坏数据、非法凭据和过大载荷错误；
- 本地副本与服务器副本恢复。

### Cloudflare 预览

- 用户创建案例并自动保存；
- 刷新后读取最近成功快照；
- 两个案例互不串线；
- 服务器失败时显示本地副本状态；
- 重试不会产生重复案例和事件；
- 旧 revision 返回冲突且不覆盖新数据；
- 管理员读取完整时间线；
- 用户反馈正确绑定；
- 删除或失效链接不能读取；
- 应用、知识、决策版本完整记录。
- 邀请链接可以进入试用入口；非邀请入口不能绕过邀请限制创建或读取案例；
- 管理员入口需要独立保护，普通案例访问凭据不能升级为管理员权限；
- 公开错误响应和日志不包含访问凭据、完整主诉、内部堆栈或其他不必要的敏感信息；
- 当前版本标识、基本错误日志和失败请求关联到案例/事件，但不泄露匿名案例的访问秘密。

详细要求见[试用持久化测试文档](./pilot-persistence-test-plan.md)。

## 9. 执行节奏和运行成本

### 开发中

- 修改样式：L0 + 相关页面冒烟；
- 修改决策：相关 L1/L2 + 对应 L3 场景；
- 修改保存/API：相关 L1/L2 + L4；
- 新增真实缺陷：先增加最小回归场景，再修代码；
- 每完成一个 A/B 场景，立即补齐页面断言并回写覆盖矩阵，不把证据留到整批结束后补记。

- 全量规则和流程测试；
- 本次修改相关的浏览器场景；
- 失败时保留证据，不用最终总结页掩盖中间错误。

### 预览部署前

- 全部 L0～L3；
- 本地 D1 保存恢复；
- P0 浏览器场景连续三次；
- 预览环境 L4 全部通过。

### 正式试用前

- P0、P1 场景全部通过；
- 预览环境无未解决的数据、权限和安全问题；
- 人工普通用户走读和专业走读完成；
- 当前版本号、错误日志和反馈入口可用。
- 邀请链接、管理员保护、案例删除和失效链接必须各有一次真实环境验证记录。

本地 L0～L2 通常为秒级；浏览器场景按多个进程并行执行；预览测试主要消耗 Worker 请求和 D1 读写；任何一层都不会因为测试数量直接消耗模型 Token。

## 10. 通过标准

### P0 阻断问题

以下任何一项失败，都不能开放试用：

- 安全停止失效；
- 权限越界；
- 不同动作错误复用复测；
- 未知被当作正常；
- 处理或训练加重后继续原计划；
- 案例串线或旧版本覆盖新版本；
- 保存后恢复到错误案例或错误阶段；
- 页面跳步、死循环、空白页或无明确出口。

### P1 发布问题

- 关键处理、复测或训练提示缺失；
- 返回修改后旧计划未失效；
- 训练反馈门槛不一致；
- 肿胀、力量、未知和低刺激出口不明确；
- 浏览器运行时错误；
- 预览环境版本和事件记录不完整。

### P2 改进问题

- 文案理解度；
- 图片和动作说明；
- 移动端细节；
- 跨浏览器表现；
- 非阻断性能和视觉问题。

## 11. 测试整改实施方案

### 11.1 整改目标

本轮整改不以增加测试条数为目标，而以减少“自动化全绿、人工随手操作立即发现问题”为目标。一个浏览器场景只有同时证明以下四件事，才算通过：

1. **路径正确**：用户确实通过可见控件到达目标页面，没有注入内部状态或依赖碰巧匹配的第一个按钮。
2. **决策正确**：每个关键选择都产生规定的下游影响，且禁止内容没有出现。
3. **状态正确**：返回、修改、保存、刷新和并发操作后，记录、版本、队列和失效范围正确。
4. **呈现正确**：关键内容可见、可读、可操作，没有明显换行、遮挡、弱边界和错误素材。

只验证最终页、运行时错误为零或脚本退出码为零，均不能单独作为场景通过证据。

### 11.2 先用历史缺陷验证测试方法

先建立“已知缺陷回放集”，用过去人工走查发现的问题检验新测试体系，而不是直接相信新的测试写法。首批至少包含：

| 缺陷类型 | 新测试必须捕获的回归 |
| --- | --- |
| 决策链 | 功能动作无法完成，处理完成后却跳过“现在这个动作能完成了吗？” |
| 动作身份 | 不同动作错误复用同一复测结果，或同一动作被当成不同动作 |
| 状态失效 | 返回修改上游答案后，旧处理、复测或训练仍然保留 |
| 控件呈现 | “重写症状描述”等关键按钮过小或边界不可辨认 |
| 布局呈现 | 动作补充区间距过紧、`1/5` 换行、关键刻度说明弱化 |
| 内容资产 | 需要真人动作图的位置重新出现未审核的 SVG 示意图 |

验证方式：为每类缺陷先写一个能在错误实现上失败、在正确实现上通过的测试；随后临时反转对应分支或样式，确认测试确实变红。不能捕获对应历史缺陷的测试，不进入发布门禁。

### 11.3 浏览器测试架构

浏览器测试改用统一运行器，业务场景不再各自负责启动浏览器、猜测按钮、等待固定毫秒和清理进程。建议结构：

```text
tests/browser/
  scenarios/       # 每个 scenarioId 的输入、操作和检查点
  contracts/       # 设计规则到预期/禁止结果的合同
  drivers/         # 只封装用户可见的填写、选择、返回、保存操作
  oracles/         # 决策链、状态、持久化、视觉和可访问性判定
  exploration/     # 通过真实页面控件执行的有种子状态探索
  fixtures/        # 案例输入、账号/邀请和环境数据
  support/         # 启动、清理、截图、trace、日志和报告
```

具体约束：

- 使用 `@playwright/test` 统一管理项目、并发、重试、超时、trace、截图、视频和 HTML 报告；
- 场景通过 `scenarioId` 与覆盖矩阵关联，场景文件只描述业务意图，不复制通用点击代码；
- 端到端场景禁止写入 `localStorage`、`sessionStorage` 或 React 内部状态；必须注入状态的用例单独标记为“页面边界测试”；
- 发布场景禁止使用宽泛的 `.first()`、`下一个按钮` 或候选文本循环推进；目标元素必须具有唯一语义角色、标签或稳定测试标识；
- 等待条件使用页面状态、响应或元素变化，不用固定 `waitForTimeout` 判断业务完成；
- 运行器统一执行 `try/finally` 清理浏览器和测试数据；每次运行使用唯一 `runId`；
- 失败统一保存：当前 URL、scenarioId、步骤号、操作轨迹、DOM、截图、trace、控制台错误、网络错误和脱敏后的案例/版本标识。

### 11.4 场景合同和逐步检查点

每个固定场景必须声明操作意图和逐步检查点，不能只写一串点击。结构至少包括：

```ts
{
  scenarioId: "RET-03",
  intent: "功能动作无法完成后，处理完成仍复测同一动作",
  inputs: { /* 固定用户输入 */ },
  checkpoints: [
    {
      after: "选择动作无法完成",
      visible: ["无法完成的原因"],
      absent: ["动作已经恢复"],
      state: ["该动作保持未解决"]
    },
    {
      after: "完成对应处理",
      visible: ["现在这个动作能完成了吗？"],
      absent: ["直接进入康复总结"],
      state: ["复测 actionId 与原动作相同"]
    }
  ]
}
```

每次会改变业务状态的点击后，至少执行以下五类断言中的相关项：

1. **页面断言**：标题、当前问题、已选值、按钮启用状态和步骤位置正确。
2. **正向决策断言**：目标检查、处理、复测、训练或停止出口出现。
3. **反向决策断言**：不相关动作、旧计划、错误成功提示或越权入口不出现。
4. **记录断言**：案例、康复记录、事件、actionId、revision 和版本关系正确。
5. **呈现断言**：关键控件尺寸、换行、遮挡、对比度、焦点和素材类型符合验收值。

### 11.5 三套真实页面测试

#### A. 固定决策场景

覆盖已知规则和高风险组合，输入和出口完全确定。首批门禁至少包括：

- 明确主诉动作正常后继续下一候选；
- 多个功能动作分别进入检查和复测；
- 同一动作复测复用与不同动作结果隔离；
- 无法完成、未知、正常、异常四类结果各自的出口；
- 疼痛、肿胀、麻电同时出现时安全出口优先；
- 活动正常但功能疼痛、活动受限但不疼、功能正常但按压不适；
- 处理有效、无变化、部分改善、加重和动态插队；
- 权限撤销后旧计划失效；
- 返回修改后只清除受影响的下游数据；
- 后续康复、新症状、训练退阶和次日反应；
- 保存刷新、两个窗口冲突、案例隔离；
- 邀请、普通案例权限和管理员权限隔离。

#### B. 真实页面状态探索

用有种子的随机操作驱动真实页面，而不是自建简化状态。探索器从当前 DOM 中读取合法可见操作，并按风险加权执行：选择、取消、返回、修改、跳过、无法完成、未知、无变化、加重、快速双击、保存、刷新和断网恢复。

每一步都运行通用不变量：

- 同一时刻只有一个有效阶段和一个明确主任务；
- 必填信息不完整时不能越过当前阶段；
- 不出现空白、重复或已经失效的检查/处理卡片；
- 每个处理目标都有前置评估证据；
- 每项处理后存在对应复测，或存在明确的不可复测/停止原因；
- 修改上游信息后，下游旧结果按依赖关系失效；
- 未知不能被计为正常，无法完成不能被计为已改善；
- 记录次数不因刷新、重试或重复保存增加；
- 本地、页面和服务器显示的保存状态不互相矛盾；
- 页面始终存在下一步、返回、保存、停止或明确完成出口。

开发提交运行较小种子集，夜间或正式试用前运行扩大种子集。任何失败必须输出种子和完整操作轨迹，并转成一个固定回归场景。

#### C. 人工任务式探索

自动化不能判断所有医学表达和使用感受。预览发布前由普通用户视角和专业人员视角各完成一次不提供点击脚本的任务式走查，只给目标，例如“记录两个动作问题并完成一次康复”“中途发现原答案填错并修改”。

人工走查重点记录：

- 不知道下一步该做什么；
- 页面结论与刚才选择矛盾；
- 处理、复测或训练理由无法理解；
- 明显按钮、间距、图片、文案和反馈入口问题；
- 虽然能继续，但用户会自然选择错误入口的情况。

发现的问题必须归入设计规则、实现缺陷或纯体验问题；可重复的前两类在修复前转成自动回归。

### 11.6 视觉和交互判定

视觉测试只选择容易影响操作的关键页面，不追求所有像素完全一致：

- 新评估首页和教程聚焦层；
- 症状描述与动作选择；
- 评估题头、进度和 NRS 滑条；
- 处理卡片、复测卡片和训练反馈；
- 康复总结、案例编号和问题反馈；
- 典型桌面宽度与一个移动端宽度。

检查分为两类：

1. **几何/语义断言**：最小点击区域、元素不重叠、关键文本不截断、`1/5` 不换行、焦点可见、图片来自已审核资产清单。
2. **视觉基线**：只对上述关键检查点做截图差异比较；基线变化必须人工确认，不能自动覆盖旧基线。

### 11.7 测试有效性门槛

新的测试体系投入使用前，必须通过以下“测试测试”：

1. 历史缺陷回放集全部能够在错误实现上失败。
2. 对 P0 规则做定向变异：删除复测、交换 actionId、把未知改成正常、保留失效计划、移除权限判断、允许旧 revision 覆盖新数据；每个变异都必须至少触发一条对应测试失败。
3. 固定场景中不存在依靠宽泛 `.first()` 或候选循环走到终点的发布证据。
4. 每条 P0 场景至少包含一个正向断言和一个禁止内容断言，并在关键状态变化后设检查点。
5. 覆盖矩阵由场景清单和最近结果生成或校验，文档数字不能人工猜测。
6. 连续三轮通过只证明稳定性；上述有效性门槛未满足时，三轮全绿仍不能发布。

### 11.8 统一命令和运行节奏

目标命令分层如下，具体时长在首轮实现后以实测值校准：

| 命令 | 内容 | 触发时机 | 初始预算 |
| --- | --- | --- | --- |
| `test:fast` | 类型、核心规则、流程状态和相关服务测试 | 开发中频繁运行 | 3 分钟内 |
| `test:integration` | 本地 D1 真实 HTTP 合同：邀请、幂等、修订、冲突、隔离、反馈、删除、权限和载荷上限 | 数据/API 修改后、本地预览前 | 5 分钟内 |
| `test:browser:target` | 本次修改绑定的固定浏览器场景 | 修改页面/流程后 | 5 分钟内 |
| `test:browser:p0` | 全部 P0 固定决策场景 | 提交前、预览前连续三次 | 15 分钟内 |
| `test:browser:full` | P0、P1、视觉和跨浏览器 | 预览部署前、正式试用前 | 45 分钟内 |
| `test:explore` | 真实页面有种子状态探索 | 夜间、正式试用前 | 30 至 60 分钟 |
| `test:preview` | 预览 D1、邀请、权限、日志和版本 | 每次预览发布后 | 按环境实测 |

`npm test` 必须清楚表明自己覆盖哪些层；浏览器测试不能隐藏在手工运行的散落脚本中。运行报告按层分别展示，禁止用代码测试总数代替真实浏览器场景数。

### 11.9 具体实施顺序

1. 引入统一 Playwright Test 运行器、目录、报告和清理机制，接管现有浏览器脚本。
2. 建立历史缺陷回放集，先证明新体系能够发现已经出现过的六类问题。
3. 抽取页面 driver、决策 oracle、状态 oracle、视觉 oracle 和证据收集模块。
