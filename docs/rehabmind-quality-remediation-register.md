# RehabMind 项目质量审查与整改登记

更新日期：2026-08-22

## 用途

本文只登记项目审查发现、整改优先级、验收标准和当前状态，不新增或修改产品、决策与临床规则。规则仍以文档中心列出的四份正式文档为准。

当前执行口径：内部逻辑整改不再以真实浏览器自动化为常规门禁。浏览器相关编号保留用于历史证据、界面人工验收或未来确有必要的发布检查；本轮逻辑覆盖以正式生产函数、流程状态轨迹、组合不变量、错误注入和 D1/API 集成为准。任何编号都不能用源码存在、简化模型通过或页面到达终点单独标记为已通过。

状态统一使用：`待整改`、`整改中`、`待验证`、`已通过`、`接受风险`。只有提供可复现的自动化证据或人工验收记录后，才能标记为 `已通过`。

## 整改顺序

1. 先处理数据身份、保存一致性、审计可信度和自动保存承诺：`DATA-01` 至 `DATA-04`、`AUDIT-01`、`AUDIT-02`、`SAVE-01`。
2. 再补齐隐私、安全、版本和可复现发布门槛：`PRIV-01`、`SEC-01`、`REL-01`、`REL-02`、`DEPLOY-01`。
3. 重建测试入口与证据体系：`TEST-01` 至 `TEST-13`。本阶段先让测试能够真实发现问题，再扩大场景数量。
4. 随后处理架构、恢复、冲突、反馈、日志与删除语义：`ARCH-01`、`DATA-05`、`DATA-06`、`FEED-01`、`OPS-01`、`PRIV-02`。
5. 最后完成管理工作台、素材验收和可访问性：`ADMIN-01`、`CONTENT-01`、`UX-01`。

测试整改的框架、场景合同、状态探索、视觉判定、有效性门槛和统一命令，统一以[测试整改实施方案](./rehabmind-test-plan.md#11-测试整改实施方案)执行。

## 发布约束

- P0 未全部达到 `已通过`，不得开放正式粉丝群试用。
- P1 未通过时，只能在明确限定范围的预览环境验证；每一项必须有责任人、风险说明和复验日期。
- 用户或人工走查发现的缺陷，必须先补可失败的复现场景，再修实现；修复后同时运行定向回归与 P0 浏览器场景。
- 覆盖矩阵只登记有证据的状态。源码中存在分支、脚本到达终点或人工口头确认，都不能单独算作覆盖完成。
