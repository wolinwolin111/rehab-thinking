# RehabMind App 入口、移动体验与测试效率优化方案

> 状态：第 1 至第 10 步已完成；当前等待第 11 步 VPS 网页用户任务验收。正式签名 APK 继续后置，但内部 debug WebView 壳可提前建立用于真实 Android 走读。
>
> 更新时间：2026-08-25。
>
> 本文只定义本轮产品体验、测试入口、部署收口和 App 交付的施工方案，不修改康复决策规则，也不代表动作图片或独立临床审核已经完成。

## 1. 本轮决策

本轮采用以下已经确认的方向：

1. 取消邀请链接和邀请码入口，用户安装 App 后自行创建匿名案例。
2. 首次创建案例时选择来源渠道，后台按渠道、案例和康复记录统计。
3. 复用康复管理系统的 Android WebView 纯壳 App 形式，不用 Capacitor 重写现有项目。
4. 取消五步聚焦教程，只保留一张极短的产品价值页；其余帮助在真实任务发生时就地出现。
5. 症状入口使用有结构的描述提示，不能承诺任意自然表达都能稳定解析。
6. 普通用户界面减少同时可见的内部流程解释，优先显示恢复情况、当前任务和下一步。
7. 手机端不压缩桌面三栏，不允许用户依靠左右滑动才能看全主要页面。
8. 增加受保护的测试工作台，用正式业务函数和 SQLite 快速创建隔离测试案例。
9. Cloudflare Worker、D1、Wrangler 和预览环境方案全部退出当前实现与现行运维文档。
10. 当前 A0-B6 的结构治理成果继续保留；本轮不重新合并阶段组件，也不修改临床候选关系。

## 2. 产品入口流程

### 2.1 目标流程

```text
启动 RehabMind App
→ 产品价值页
→ 选择来源渠道
→ 数据使用说明
→ 创建匿名案例
→ 描述当前问题
→ 进入后续康复
```

首次使用不展示工作台截图、六阶段说明、服务器、本机草稿、案例同步或内部决策流程。

### 2.2 产品价值页

页面使用完整首屏，不叠加在工作台之上。

小标题：

**悦舒运动康复**

主标题：

**你的线上康复助手**

说明：

**把悦舒运动康复的线下经验带到你身边，陪你完成每一次康复。**

主要按钮：

**开始康复**

次要入口：

**继续以前的康复**

本页不出现以下内容：

- 检查、处理、复测和训练等内部阶段名称；
- “帮助你看清哪些方向值得继续”等抽象结果描述；
- 保存到本机或同步到服务器的技术区别；
- AI、规则引擎、案例凭证和开发者边界说明；
- 五步教程进度、聚焦遮罩和被指向的工作台控件。

### 2.3 来源渠道

点击“开始康复”后，从底部弹出一个单问题选择面板。

标题：

**你从哪里了解到我们？**

固定选项：

- 抖音粉丝群；
- 抖音评论区；
- 小红书；
- 朋友推荐；
- 悦舒工作室；
- 其他。

约束：

- 一次点击即可选择，不要求输入邀请码；
- 不向用户解释渠道统计用途；
- “其他”允许补充不超过 40 个字符；
- 来源是案例属性，不是权限凭证；
- 测试工作台创建的案例自动使用 `internal_test`，不显示本题。

### 2.4 数据使用说明

标题：

**开始前，请确认数据使用方式**

默认显示三条关键信息：

- 康复内容会使用匿名案例编号保存；
- 不需要填写姓名、手机号等身份信息；
- 用户可以在应用内删除案例。

完整内容放入“查看完整说明”，不在默认首屏形成协议墙。

确认项：

**我已了解并同意以上内容**

按钮：

- **同意并创建案例**；
- **暂不使用**。

拒绝后不创建案例、不上传健康内容、不进入完整工作台，也不再提供可无限使用的“仅本机模式”。

### 2.5 问题描述入口

标题：

**请描述你的问题**

说明：

**请说明不适部位、出现时间、受影响的动作和恢复目标。**

输入框上方使用短提示：

```text
不适部位 · 出现时间 · 受影响动作 · 恢复目标
```

示例：

**例如：右脚踝昨天扭伤，走路和下楼时疼，恢复目标是正常走路。**

补充说明：

**不清楚的内容可以写“不清楚”。**

按钮：

**继续**

实现约束：

1. 不使用“按你自己的话说就行”等可能暗示任意表达都可稳定解析的承诺。
2. 首次文本只负责形成候选信息，用户必须在后续确认结构化字段。
3. 缺失项目通过单题追问补充，不通过扩大字符串猜测规则强行推断。
4. 解析失败时保留原文，明确告诉用户需要补充哪一项。
5. 用户修改原文后，受影响的结构化信息和后续结果按现有失效规则重新确认。

### 2.6 统一用词

本轮统一使用以下表达：

| 使用场景 | 统一文案 |
| --- | --- |
| 用户要解决的问题 | 问题 |
| 用户希望恢复的结果 | 恢复目标 |
| 一次完整使用 | 本次康复 |
| 后续继续使用 | 后续康复 |
| 操作结束按钮 | 已完成 |
| 操作结束并推进 | 已完成，继续 |
| 首次症状提交 | 继续 |
| 回看数据 | 本次记录 / 康复记录 |

“希望恢复的活动”不再作为界面固定术语，统一改为“恢复目标”。“完成了”不再作为操作按钮，但自然语句不做机械替换。

## 3. 就地提示系统

取消一次性五步教程后，只在用户第一次真正遇到相关功能时显示一句提示。

| 出现时机 | 提示内容 | 展示方式 |
| --- | --- | --- |
| 首次填写问题 | 请包含不适部位、出现时间、受影响动作和恢复目标 | 输入框附近，首次常驻 |
| 首次自动保存成功 | 已保存，下次打开可以从这里继续 | 轻提示，自动消失 |
| 首次生成案例编号 | 反馈问题时，可以把这个编号告诉我们 | 案例编号旁，一次性提示 |
| 首次打开康复记录 | 这里可以查看以前的恢复情况 | 页面内提示 |
| 首次进入复测 | 再试一次刚才的动作，看看现在有没有变化 | 复测标题下方 |
| 首次修改旧答案 | 修改后，受影响的后续内容需要重新确认 | 修改确认框 |

约束：

- 提示不阻挡当前主操作；
- 同一提示完成或关闭后不重复出现；
- 帮助入口保留在更多菜单中，可重新查看；
- 安全停止信息不属于教程，触发时必须直接显示。

## 4. 信息密度规则

### 4.1 页面基本结构

每个操作页面使用统一顺序：

```text
当前阶段与进度
→ 当前问题
→ 一句必要提示
→ 当前选项或操作
→ 主要按钮
→ 按需展开的帮助
```

默认首屏最多同时出现：

- 一个阶段标识；
- 一个主问题；
- 一句必要说明；
- 一组当前选项；
- 一个主要按钮。

### 4.2 四层信息

| 层级 | 内容 | 默认状态 |
| --- | --- | --- |
| 第一层 | 当前问题、选项和主要按钮 | 始终显示 |
| 第二层 | 完成当前操作必需的一句话 | 始终显示 |
| 第三层 | 示例、怎么做、判断方法 | 按需展开 |
| 第四层 | 专业依据、完整记录、问题台账 | 专业模式或记录页 |

安全停止条件、数据丢失风险和无法继续的原因不折叠。

### 4.3 六阶段调整

#### 症状信息

- 默认只显示“请描述你的问题”、结构提示、输入框和“继续”；
- 示例可展开，但首次为空时允许直接显示一条短示例；
- 已收集信息不常驻占据手机首屏。

#### 关键确认

- 一次只问一个问题；
- 风险解释只在命中相关选项后出现；
- 普通答案不提前显示医学分流说明。

#### 评估检查

- 首屏只显示当前动作、一个简短做法、结果选项和进度；
- “怎么做”展开完整动作方法和观察重点；
- 选择“出现不适”后才询问位置、感觉和分数；
- 选择“无法完成”后才询问原因和替代动作；
- 专业记录与普通用户选项分层显示。

#### 后续康复与复测

- 一次只显示一个当前操作；
- 用户点击“已完成”后，在同一区域切换到对应复测；
- 结果优先显示前后变化，例如 `6 → 3` 或“现在可以完成”；
- 候选排序、处理依据和内部队列不在普通用户界面常驻。

#### 康复训练

- 一次只显示一个训练动作；
- 首屏只保留动作名称、次数、必要要点、动作图和“已完成”；
- 退阶、进阶和专业说明按需展开；
- 完成后再询问“更轻松、差不多、更不舒服”。

#### 康复总结

首屏优先回答：

1. 今天有没有改善；
2. 当前恢复到哪里；
3. 下次从哪里继续。

完整检查、操作和训练记录放入“查看本次详细记录”。

## 5. 手机端布局

### 5.1 总体结构

手机端不压缩桌面三栏，改为：

```text
顶部状态栏
阶段进度
当前任务内容
底部操作栏
按需出现的阶段抽屉或记录抽屉
```

主页面示意：

```text
┌─────────────────────────┐
│ RM  第1次康复     已保存  ⋮ │
├─────────────────────────┤
│ 1/6  症状信息       查看阶段 │
│ ━━━━━━━─────────────── │
├─────────────────────────┤
│ 请描述你的问题            │
│                         │
│ 不适部位 · 出现时间        │
│ 受影响动作 · 恢复目标      │
│                         │
│ ┌─────────────────────┐ │
│ │ 右脚踝昨天扭伤……      │ │
│ │                     │ │
│ └─────────────────────┘ │
│                         │
│ 不清楚的内容可以写“不清楚” │
├─────────────────────────┤
│ 本次记录              继续 │
└─────────────────────────┘
```

### 5.2 顶部状态栏

始终只保留：

- RehabMind 标识；
- 当前康复次数；
- 保存状态；
- 更多菜单。

案例编号、问题反馈、康复记录、帮助和版本放入更多菜单或对应独立页面，不全部挤在顶部。

### 5.3 阶段导航

手机端不显示六个并排小标签，也不使用需要横向滑动的阶段条。

默认只显示：

```text
3/6 评估检查                         查看阶段
```

点击“查看阶段”后打开全屏抽屉：

```text
本次康复                                      关闭

✓  症状信息
✓  关键确认
●  评估检查                                   当前
4  后续康复                                   未开始
5  康复训练                                   未开始
6  康复总结                                   未开始
```

已完成阶段可以回看，未解锁阶段显示但不可点击。关闭后恢复原页面和原滚动位置。

### 5.4 本次记录

桌面右侧的已收集信息在手机端改为底部抽屉。

入口：

**本次记录 4项**

抽屉内容按“字段名称 + 当前答案”纵向排列。抽屉只负责查看；点击可修改项目时，关闭抽屉并返回对应页面，不在抽屉内部继续套弹窗。

### 5.5 康复记录

康复记录使用独立页面，不放进小抽屉。结构为：

```text
返回  康复记录

案例 RM-8K3F2Q

第3次康复 · 进行中
当前不适 3/10
继续康复

第2次康复 · 已完成
6 → 3
查看总结
```

案例与多次康复记录必须在视觉层级上明确区分。

### 5.6 底部操作栏

底部操作栏最多包含一个主要操作和一个次要入口：

```text
本次记录                                      继续
```

要求：

- 主要按钮高度不小于 48px；
- 输入键盘弹起时操作栏不能遮挡当前字段；
- 页面需要为 Android 安全区域预留底部空间；
- 页面内容不能被固定操作栏覆盖；
- 没有下一步时不显示空的固定栏。

## 6. 禁止横向滚动

### 6.1 产品规则

在支持的手机宽度下，用户必须通过纵向滚动完成所有主要任务。不得要求用户左右滑动才能看全：

- 标题或说明；
- 输入框；
- 结果选项；
- 阶段进度；
- 评分刻度；
- 动作图片；
- 处理和复测按钮；
- 康复总结；
- 案例编号和反馈入口。

主要流程不使用横向轮播、横向表格、横向阶段标签或超宽卡片。

### 6.2 布局约束

1. 所有 grid 子项设置 `min-width: 0`，轨道使用可收缩的 `minmax(0, 1fr)`。
2. 两列选项在窄屏放不下时改为单列，不缩小文字硬塞。
3. 标签和提示词允许自然换行，不使用固定最小宽度撑开页面。
4. 图片使用 `max-width: 100%` 和稳定宽高比，不能按原始像素撑开容器。
5. 长案例编号和技术错误使用可控换行或省略显示，并提供复制按钮。
6. 桌面表格在手机端改成纵向条目，不在主流程内出现横向滚动表格。
7. 弹窗、抽屉和输入控件宽度不能超过 `100vw` 扣除安全边距后的空间。
8. `overflow-x: hidden` 只能作为最后保护，不能用来掩盖被裁切的内容。

### 6.3 验收宽度

至少验证：

- 320×568；
- 360×800；
- 390×844；
- 412×915；
- 430×932。

每个关键页面满足：

```text
document.documentElement.scrollWidth <= document.documentElement.clientWidth + 1
```

同时人工确认没有被裁切但无法访问的内容。

## 7. 视觉标准

- 继续沿用现有品牌色，不建立另一套孤立的 App 主题；
- 页面背景保持安静，主内容用清晰分区而不是多层嵌套卡片；
- 卡片圆角不超过 8px；
- 页面标题约 24px，正文 16px，辅助文字 14px，不按视口宽度缩放字体；
- 所有触控按钮和选择项高度不小于 48px；
- 一屏只设置一个主要按钮；
- 阶段数字、评分和前后变化使用稳定宽度，避免选择后布局跳动；
- 底部抽屉最高约占屏幕 75%，内容超出后只做内部纵向滚动；
- 不在抽屉中继续嵌套卡片、抽屉或模态框。

## 8. 测试工作台

### 8.1 入口和权限

新增独立入口：

```text
/RehabMind/test
```

访问规则：

- 本地开发环境可以直接进入；
- VPS 环境必须具有有效管理员会话；
- 普通用户和 App 首页不显示测试入口；
- 管理后台提供“测试工作台”入口。

### 8.2 三类测试模式

#### 完整流程测试

只预填最初的问题描述，从症状入口按真实页面继续。该模式可以作为真实业务流程证据。

#### 页面定向测试

加载到指定阶段，快速检查评估、后续康复、复测、训练和总结的页面接线。该模式必须标记为“页面边界测试”，不能冒充完整流程。

#### 决策实验室

复用现有 `decision-lab`，展示输入对应的生产决策函数输出，不创建正式案例，也不代替产品纵向流水线。

### 8.3 起点模板

首批至少提供：

- 单侧膝关节动作疼痛；
- 单侧踝扭伤；
- 双侧问题与优先侧；
- 明显肿胀；
- 麻木或力量变化；
- 高不适停止；
- 动作无法完成；
- 后续康复后改善；
- 后续康复后无变化；
- 后续康复后加重；
- 训练后加重；
- 第二次康复；
- 出现新问题；
- 返回修改旧答案。

### 8.4 数据隔离

测试案例增加：

```text
isTestCase
testRunId
scenarioId
createdBy
```

规则：

- 测试案例继续使用正式 orchestrator、service、repository 和 SQLite；
- 测试案例编号明确显示测试标识；
- 默认不进入渠道转化、用户完成率和正式反馈统计；
- 后台可以单独筛选测试案例；
- 支持按 `testRunId` 批量删除；
- 深层快照测试与完整流程测试在报告中分开计数。

### 8.5 效率功能

测试工作台提供：

- 重新开始当前场景；
- 复制当前场景为新测试案例；
- 清除当前设备草稿；
- 复制案例编号；
- 打开对应后台记录；
- 删除本次运行产生的全部测试案例；
- 显示当前 App、知识库和决策版本。

## 9. 取消邀请制

邀请链接不再参与案例创建。目标结构为：

```text
渠道来源
→ 匿名案例编号
→ 设备访问凭证
→ 多次康复记录
→ 事件和问题反馈
```

实施要求：

1. 来源渠道写入案例，但不作为权限凭证。
2. 案例编号公开显示，但不能单独读取健康记录。
3. App 保存随机设备访问凭证。
4. 卸载或更换手机通过独立恢复码恢复，不能只输入案例编号。
5. 取消邀请后继续保留请求大小限制、频率限制和幂等创建。
6. 服务端必须校验数据使用同意记录，不能只依赖前端按钮状态。
7. 旧邀请字段暂时保留为可空历史字段，不执行破坏性删除迁移。
8. 邀请访问、转化率和失效链接指标从当前后台中移除，替换为渠道到案例、案例到首次完成的指标。

## 12. 对当前项目的影响

| 改动 | 影响程度 | 影响范围 | 不应改变 |
| --- | --- | --- | --- |
| 入口文案 | 低 | onboarding、症状标题、组件合同 | 决策结果 |
| 信息密度 | 中 | 六阶段视图、CSS、移动布局 | 领域规则与状态含义 |
| 首次使用流程 | 中高 | 首次状态机、同意、遥测、案例创建时机 | 历史案例内容 |
| 取消邀请 | 高 | API、service、repository、后台指标、测试 | 案例访问隔离 |
| 测试工作台 | 中高 | 测试字段、管理筛选、批量清理 | 正式统计和正式业务函数 |
| Cloudflare 清理 | 中高 | 构建、依赖、数据库入口、运维文档 | VPS 发布和 SQLite 数据 |
| 手机适配 | 中高 | 导航、侧栏、弹层、输入与响应式 CSS | 六阶段业务合同 |
| WebView APK | 中高 | 独立 Android 外壳、版本和设备恢复 | Web 业务代码所有权 |

兼容原则：

- 数据库只做向前兼容迁移；
- 旧案例来源为空时显示“历史来源/未记录”；
- 旧邀请字段不立即物理删除；

- 当前主工作台继续承担状态协调，新增入口状态优先放入独立模块；
- 用户可见入口和构建发生变化后，旧 A7 `15/16` 证据不得继续作为当前版本证据。

## 13. 测试与验收

### 13.1 内部逻辑

- 首次使用状态机：价值页、来源、同意、创建中、工作台和拒绝出口；
- 来源枚举、其他来源长度和服务端校验；
- 无邀请案例幂等创建、限流和访问凭证隔离；
- 测试案例与正式统计隔离；
- 测试案例批量清理只影响指定 `testRunId`；
- 原有评估、队列、复测、训练和恢复生产函数测试继续通过。

### 13.2 页面合同

- “请描述你的问题”和四项结构提示可见；
- 确认前不生成未经用户确认的结构化结论；
- 条件问题只在对应答案后出现；
- “已完成”进入对应复测而不是跳过；
- 折叠帮助不隐藏必填错误、安全停止或下一步；
- 手机阶段抽屉和本次记录抽屉不修改业务状态。

### 13.3 SQLite/API

- 渠道、案例、访问凭证和版本正确落库；
- 测试案例字段正确落库并默认排除正式指标；
- 旧 schema 升级后历史案例可读；
- Node/SQLite repository 是唯一运行路径；
- 取消邀请后，缺少邀请头不再导致案例创建失败。

### 13.4 最小真实界面

不恢复大量真实浏览器业务组合。业务规则和响应式布局先在网页完成；手机网页基本布局稳定后即可创建内部 debug WebView 壳，用真实 Android 设备提前发现浏览器模拟无法覆盖的外壳问题。debug 壳不对外分发，也不代表正式 APK 已验收。浏览器开发者模式用于模拟桌面和手机视口，只保留：

1. 首次启动到创建案例；
2. 描述问题到结构确认；
3. 自动保存、关闭和恢复；
4. 后续康复完成后进入对应复测；
5. 问题反馈绑定案例和康复记录；
6. 管理员测试工作台权限；
7. 320、360、390、412、430px 宽度以及桌面宽度无页面横向溢出；
8. 输入法弹出、触摸目标、底部操作栏和抽屉在手机模拟视口中可操作。

验证分五层：浏览器多视口检查布局；Android Emulator 扩展系统版本、分辨率、旋转、系统字体和软键盘组合；真实 Android Chrome 检查触摸、弱网和浏览器存储；真实手机上的内部 debug WebView 壳检查系统返回、进程重开、Cookie/IndexedDB、外链、下载、断网与加载失败；网页和 VPS 验收通过后再用正式签名 release candidate 检查安装、覆盖升级、签名、versionCode 和正式域名。APK 不重复穷举全部康复分支，但必须复用内部场景工作台选取关键场景走真实 WebView 链路。

### 13.5 人工任务

由首次接触者回答：

- 是否理解 RehabMind 是什么；
- 是否知道为什么需要描述这些信息；
- 是否知道当前恢复到哪里；
- 是否能完成一个页面而不阅读大量说明；
- 是否能找到案例编号、康复记录和问题反馈；
- 手机上是否存在必须左右滑动才能操作的页面。

## 14. 执行顺序

1. 固定本文、产品规范、场景验收和数据字段合同。
2. 将构建链改为纯 Node，验证后清除 Cloudflare、D1 和 Wrangler 遗留。
3. 取消邀请门，实现来源渠道、服务端同意校验和无邀请案例创建。
4. 增加测试案例字段、受保护测试工作台和批量清理。
5. 重做首次使用流程和问题描述入口。
6. 按症状、确认、评估、后续康复、训练、总结依次整改信息密度。
7. 建立手机顶部栏、阶段抽屉、本次记录抽屉、康复记录页和底部操作栏。
8. 在本地网页完成内部逻辑门禁，并用浏览器开发者模式完成桌面与手机视口检查；手机网页基本布局稳定后建立内部 debug WebView 壳，在真实 Android 上走触摸、软键盘、返回、断网和恢复。
9. 更新测试注册表、发布门禁、运维手册和项目状态。
10. 网页本地验收通过后执行 VPS canary、SQLite 备份迁移、健康检查和回滚演练。
11. 在 VPS 网页版本完成一次人工任务验收，确认产品价值、信息密度、保存恢复和手机布局均通过。
12. 第 11 步获得产品确认后，将已有 debug 壳收口为正式 release variant，接入正式签名和自动构建；完成安装、覆盖升级、可信地址和外壳专项验收后再对外发包。

## 15. 暂不纳入本轮

- 动作图片生成、来源授权和动作准确性审核；
- 独立临床内容审核；
- 多关节、上肢、脊柱和骨盆入口；
- 继续拆分已经通过 B0-B6 门禁的主工作台；
- 用大量真实浏览器场景穷举内部康复组合；
- Cloudflare 预览或正式环境恢复。

这些事项不得被写成已经完成，也不得阻塞本文中已经明确的 App 首批试用施工，除非后续产品决定改变开放条件。
