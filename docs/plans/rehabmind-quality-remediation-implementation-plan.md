## 1. 文档定位

本文是后续执行者的施工手册，覆盖质量整改登记中的全部 34 项。本文不修改产品、临床或决策规则；遇到规则含义不明确时，必须回到文档中心的四份正式文档确认，不能由执行者自行补出新的康复逻辑。

本文最初用于约束施工顺序；当前执行已经完成本地 P0 三轮、预览核心部署验收和主要网络异常场景，进入发散组合、纯用户路径、日志出口和正式试用环境隔离批次。已完成的实现与证据以[质量审查与整改登记](../quality/rehabmind-quality-remediation-register.md)及测试报告为准；尚未通过完整验收的项目仍保持“整改中”或“待整改”。

本轮续执行结果：关键页面视觉基线已建立并通过 3/3；隔离、保存中刷新/超时和急性高风险远程脚本已补成功路径清理，失败路径的全局 runId 清理仍未完成。RET-03 的 IndexedDB 边界夹具仍可通过，但当前膝关节真实用户路径没有自然触发复用分支，故不升级为纯用户 E2E；Cloudflare tail 仍受日志流连接超时阻塞。预览中已确认属于本轮测试的残留案例已按精确 ID 清理，未批量删除其他活动案例。

## 本轮执行口径变更（2026-08-22）

当前执行者不再运行真实浏览器自动化来验证内部处理逻辑。原手册中要求的 P0 浏览器回归、真实页面探索、Firefox 和视觉测试保留为历史记录或可选界面验收，不作为本轮内部逻辑整改的前置条件。内部逻辑的通过证据改为：正式生产函数、状态转换轨迹、组合不变量、错误注入、D1/API 集成和必要的人工界面验收。

本轮不得为了测试方便复制一套页面外的业务规则。若主页面中的流程编排无法直接测试，先补特征测试，再只提取当前链条需要的高内聚函数；提取一段、测试一段、回归一段，不进行一次性总状态机重构。

## 2. 执行总原则

1. **先证明问题，再改实现**：每项整改先提交失败测试或人工复现证据，再修改代码。
2. **一项一个责任边界**：页面、流程状态、持久化、仓储、接口和展示分层修改，禁止继续把逻辑堆进主页面组件。
3. **不静默丢数据**：迁移、冲突、删除、恢复失败时，优先保留可导出的用户数据和明确提示。
4. **不拿测试数量代替产品证据**：规则测试、D1 集成、真实浏览器、视觉和人工走查分别报告。
5. **数据库只向前迁移**：每个 D1 变更使用新 migration；不修改已经执行过的 SQL 文件。
6. **预览先行**：所有 schema、API、邀请、权限和日志改动先进入独立预览环境，通过后才允许正式试用。
7. **安全默认拒绝**：认证、邀请、未知事件类型、损坏快照和不兼容版本都应拒绝或进入明确恢复路径。
8. **一次只改一个批次**：每批都能独立验证和回退，不把架构拆分、数据迁移和界面重做混在一次发布中。

## 3. 每项整改的统一完成定义

一项只能从“待整改”进入“已通过”，必须同时具备：

- 对应编号的失败复现；
- 实现或配置改动；
- 定向自动化测试；
- 受影响的内部逻辑轨迹和不变量测试通过；若存在用户可见界面变化，补人工界面验收记录；
- 数据库改动具备迁移验证和回退说明；
- 用户可见行为改动具备截图或人工验收记录；
- 覆盖矩阵、整改登记和版本说明同步更新；
- 没有新增未解释的控制台错误、敏感日志或脏数据。

每项证据统一保存到 `artifacts/quality/<release>/<issue-id>/`，至少包含 `result.json`、运行日志和必要截图。该目录默认不提交用户数据；报告只保存脱敏夹具。

## 4. 开工前准备

### 4.1 固定基线

执行者首先记录：

```text
git commit / 工作树状态
Node、npm、Wrangler 版本
当前应用、知识、决策版本
本地与预览 D1 migration 列表
当前测试命令和各层实际用例数
当前 P0/P1 浏览器场景清单
```

不要把当前 34 项待整改误写成“基线通过”。基线只描述现状。

### 4.2 数据备份

在第一次改 D1 前：

1. 导出预览 D1 的 schema 和数据。
2. 记录导出时间、数据库 ID、migration 版本和应用版本。
3. 用新的临时 D1 导入并完成一次读取验证。
4. 备份文件不得进入公开仓库；只记录校验值和存储位置。
5. 未验证恢复能力前，不执行远程 migration。

### 4.3 建立整改分支与提交边界

- 一个批次至少一个独立提交；数据库 migration 与使用它的代码可放在同一批次，但必须能一起回退。
- 不提交 `.dev.vars`、邀请令牌、管理员密钥、案例访问令牌或真实健康信息。
- 每次提交说明包含整改编号，例如 `fix(DATA-01): ...`。

## 6. 测试整改施工方案

测试的完整目标、场景合同和运行节奏见[测试整改实施方案](../quality/rehabmind-test-plan.md#11-测试整改实施方案)。本节提供文件级实施步骤。

### TEST-01：统一测试入口和依赖

**目标**：任何人运行一个命令后，都能知道实际执行了哪些层，不能再把 `npm test` 误解为全部浏览器验证。

**主要位置**：`package.json`、`package-lock.json`、现有 `tests/*.test.mjs`、`scripts/real-browser-*.mjs`。

**实施步骤**：

1. 将 `@playwright/test` 固定为 `devDependency`，不再依赖环境中偶然存在的 `playwright-core`。
2. 新建 `playwright.config.ts`，定义 `baseURL`、浏览器项目、失败截图、trace、视频、HTML/JUnit 报告、超时和 worker 数。
3. 增加命令：`test:unit`、`test:integration`、`test:browser:target`、`test:browser:p0`、`test:browser:full`、`test:visual`、`test:explore`、`test:preview`。
4. 将 `npm test` 定义为本地提交门槛，并在输出第一行明确列出包含与不包含的测试层。
5. 新建 `scripts/quality/quality-summary.mjs` 聚合各层结果，禁止只输出总测试条数。
6. 将旧浏览器脚本标记为 `legacy`；迁移完成前保留，但不得计入新门禁。

**测试与验收**：

- 从干净安装执行每条命令，不依赖全局 Playwright。
- 故意让一个浏览器断言失败，`npm test` 或对应发布命令必须非零退出。
- 报告分别显示规则、集成、浏览器、视觉和预览层数量。

### TEST-02：统一浏览器运行器与持续门禁

**目标**：浏览器测试由统一框架启动、清理、报告和阻断发布。

**主要位置**：新建 `tests/browser/`；逐步迁移 `scripts/real-browser-*.mjs`。

**实施步骤**：

1. 建立 `scenarios/`、`contracts/`、`drivers/`、`oracles/`、`fixtures/`、`support/`、`exploration/`。
2. 在 `support/environment` 中统一读取本地/预览 URL、邀请令牌和管理员测试凭据；报告中只显示是否配置，不显示值。
3. 在 `support/artifacts` 中保存 scenarioId、步骤号、操作轨迹、截图、DOM、trace、console 和失败请求。
4. 在 `globalSetup` 创建唯一 `runId`；在 `globalTeardown` 清理测试数据和残留上下文。
5. 增加提交前与预览前工作流。若仓库使用 GitHub，则在 `.github/workflows/quality.yml` 分别运行快速层和浏览器层；若未使用 GitHub，部署脚本必须调用同样的 npm 命令。
6. 部署命令只能在质量汇总文件为通过且对应 commit 未变化时继续。

**验收**：浏览器崩溃、断言失败、未捕获 pageerror、测试数据清理失败均阻断门禁，并生成可复现报告。

### TEST-03：把随机状态测试改为真实页面探索

**目标**：保留现有纯状态随机测试，但不再把它当作用户流程覆盖；新增真实页面有种子探索器。

**主要位置**：`tests/workflow/random-state-sequence.test.mjs`；新建 `tests/browser/exploration/`。

**实施步骤**：

1. 将现有测试更名或报告为 `model-state-fuzz`，明确它只验证简化模型。
2. 页面探索器只读取当前可见且可操作的语义控件，形成合法动作集合。
3. 使用可复现 PRNG，输入 `seed`、最大步骤数、操作权重和场景起点。
4. 对返回、修改、无法完成、未知、无变化、加重、双击、刷新、断网和两窗口操作提高权重。
5. 每一步执行通用不变量：阶段唯一、必填不跳过、无过期卡片、处理有依据、处理后有复测或停止原因、版本不回退、记录次数不重复、页面有明确出口。
6. 失败保存 seed、每步 DOM 摘要和操作轨迹；提供 `npm run test:explore -- --seed=<n>` 单次重放。
7. 每个稳定失败种子转成固定场景，不能永久只靠随机命中。

**验收**：临时植入“删除处理后复测”和“修改后不清旧计划”两种错误，探索器应在限定种子集内报错；失败可一键重放。

### TEST-04：删除源码文字匹配型伪证据

**目标**：测试调用真实函数、接口或页面，不通过正则检索源码证明功能存在。

**主要位置**：`tests/unit/quality/real-browser-audit-contract.test.mjs`、`tests/component/rendered-html.test.mjs`、其他读取源码后 `assert.match` 的测试。

**实施步骤**：

1. 逐个列出源码匹配测试想保护的规则。
2. 纯规则迁移为直接调用导出函数；页面呈现迁移为 Playwright 断言；构建合同仅保留真正的静态约束。
3. 无法直接测试的内部逻辑先提取为纯函数，不为测试导出页面私有状态。
4. 源码匹配测试迁移后删除，避免同一规则存在真假两份证据。
5. 对每条新测试做定向变异，确认删除实际分支时测试失败。

**验收**：P0 覆盖证据中不存在“源码含某字符串所以通过”的条目。

**当前执行状态（2026-08-22）**：核心规则已陆续迁移为正式可调用模块，并通过直接调用、组合轨迹和定向变异验证。处理队列的停止/定位、稳定目标身份、方向候选规则、候选资格合并、处理记录编排和台账联动均已有正式核心测试；`rendered-html.test.mjs`、局部路径合同等仍保留的源码/静态内容断言，当前只作为页面接线与内容合同，不计入内部逻辑覆盖；尚未完成的具体迁移项继续登记在内部逻辑覆盖矩阵，不得用这些合同替代行为测试。

### TEST-05：补齐真实 D1 仓储与 API 集成测试

**目标**：测试实际 migration、约束、事务和路由，而不只测试内存仓储替身。

**主要位置**：`db/schema/pilot-schema.ts`、`db/repository/pilot-case-repository.ts`、`drizzle/`、`app/api/pilot/`、新建 `tests/integration/d1/`。

**实施步骤**：

1. 每个测试 run 创建隔离本地 D1；从空库执行全部 migration，再重复执行迁移检查幂等管理行为。
2. 通过真实 HTTP 路由测试创建、读取、保存、幂等、冲突、反馈、删除、邀请和管理员权限。
3. 通过仓储合同测试唯一索引、条件更新、事件序列和事务原子性。
4. 模拟 snapshot 更新成功但事件插入失败，确认批处理不留下半状态。
5. 对两个案例交叉使用 token、eventId、feedback target，全部必须拒绝。
6. 测试损坏 JSON、未知 schemaVersion、超大 payload、空 token 和旧 revision。
7. 每次测试结束按 runId 清理；清理失败让测试失败。

**验收**：上述测试在本地 D1 而非内存 Map 上运行；从空库和已有上一版本 schema 两种起点均通过。

### TEST-06：端到端禁止内部状态注入

**目标**：真实 E2E 必须证明用户可通过页面到达目标状态。

**主要位置**：所有 `real-browser-*` 脚本，重点检查 `localStorage`、`sessionStorage`、`page.evaluate` 和内部 API 注入。

**实施步骤**：

1. 扫描并登记所有注入点。
2. 仅用于缩短前置步骤的用例改名为 `boundary`，报告中单独计数。
3. 每条 P0 E2E 使用页面可见控件建立状态；需要数据前置时只可通过正式公开 API，并明确它不是全链路入口证据。
4. 覆盖矩阵新增 `evidenceType`：`rule`、`boundary`、`e2e`、`preview`、`manual`。
5. 发布门槛指定需要 `e2e` 的规则不能由 `boundary` 替代。

**验收**：P0 E2E 中不存在内部存储写入；报告能够分别统计 E2E 和边界测试。

### TEST-07：去除宽泛选择器和自动推进

**目标**：场景始终执行自己声明的业务选择，不能碰巧走到终点。

**主要位置**：`scripts/legacy-browser/real-browser-fixed-scenario-helpers.mjs`、`real-browser-ret-action-identity.mjs` 等候选循环脚本。

**实施步骤**：

1. 删除发布场景对 `clickFirstFixedButton`、宽泛 `/下一步|继续/` 和候选数组循环的依赖。
2. 为重复文本控件增加稳定、面向业务的 `data-testid` 或唯一可访问名称。
3. driver 方法使用业务动作命名，例如 `chooseChiefAction("squat")`，内部断言匹配数量必须等于 1。
4. 每次点击前检查当前 scenario step；点击后检查预期页面标识。
5. 找不到目标或出现多个目标时立即失败，不继续猜测。
6. 通用自动走读器保留在 `exploration`，不得生成覆盖通过状态。

**验收**：静态检查发布场景禁止 `.first()` 和通用候选推进；场景改一个关键文案或 actionId 时会在准确步骤失败。

### TEST-08：建立视觉与几何验证

**目标**：自动发现明显的尺寸、间距、换行、遮挡和错误素材问题。

**主要位置**：`src/features/rehabmind/styles/complete-demo.css`、关键页面组件、`tests/browser/visual/`。

**实施步骤**：

1. 选定症状入口、动作选择、评估题头、NRS、处理、复测、训练、总结、案例记录和反馈弹层作为关键基线。
2. 对功能性要求写几何断言：最小点击区域、边界样式、相邻元素间距、`1/5` 单行、端点文字字号/字重、无重叠和无横向溢出。
3. 建立桌面主视口、窄桌面和一个移动视口；不要使用大量相近尺寸。
4. 使用 Playwright 截图比较；动画、时间和随机编号先固定或遮罩。
5. 基线更新必须人工查看差异图并记录原因，禁止测试脚本自动接受新基线。
6. 素材断言读取审核清单，未审核或 SVG 占位素材不得出现在正式处理/训练卡。

**验收**：临时恢复按钮弱边界、`1/5` 换行和 SVG 占位图时，对应测试分别失败。

### TEST-09：统一清理、超时和失败证据

**目标**：测试失败不残留浏览器、案例或不完整报告。

**实施步骤**：

1. 浏览器生命周期交给 Playwright fixtures，不在业务场景手写 `browser.close()`。
2. 所有服务端夹具附 `runId`；测试结束通过管理员测试接口或隔离数据库整体清理。
3. 禁止固定等待作为业务完成条件；统一使用 locator、response、revision 或保存状态等待。
4. 设置单步骤、单场景和全套超时；超时报告当前业务阶段。

## 7. 数据与保存整改施工方案

### DATA-01：等 revision 下不覆盖本地未同步状态

**问题根因**：恢复逻辑使用远端 `revision >= localRevision` 即采用远端快照，无法区分“本地干净”与“本地在同一服务器 revision 上继续修改”。

**主要位置**：`src/features/rehabmind/components/workbench/rehabmind-workbench.tsx` 的恢复与同步队列、`src/infrastructure/pilot/api/case-client.ts`、快照表。

**目标数据模型**：本地保存信封至少包含 `serverRevision`、`lastSyncedHash`、`localContentHash`、`dirty`、`pendingEventId`、`lastLocalSavedAt`。

**实施步骤**：

1. 抽取 `PilotSyncEnvelope` 和 `resolveRestoreSource(local, remote)` 纯函数。
2. 对快照做稳定序列化后计算内容 hash；不要用对象引用或时间戳判断内容变化。
3. 每次本地写入先更新 `localContentHash` 和 `dirty=true`；服务器确认后更新 `serverRevision/lastSyncedHash` 并清除 dirty。
4. 恢复规则固定为：本地干净且远端更新则用远端；本地 dirty 且远端未前进则保留本地并续传；本地 dirty 且远端已前进则进入冲突；内容 hash 相同可自动合并元数据。
5. 删除简单的 `remote.revision >= localRevision` 覆盖判断。
6. 冲突前不得修改本地快照；将远端副本单独保存在冲突上下文。

**测试**：等 revision 同内容、等 revision 本地更新、远端高 revision 本地干净、远端高 revision 本地 dirty、网络失败后恢复、两窗口保存。

**验收**：任何组合都不静默丢失本地或远端内容；冲突可复现并有明确解决入口。

### DATA-02：案例身份与主诉内容解耦

**问题根因**：当前 `caseKey` 由部位、侧别、位置和主诉文本拼接，相同主诉可能合并，修改主诉也可能改变案例身份。

**实施步骤**：

1. 新建稳定 `localCaseId`，用户点击“新建评估”时生成 UUID；之后无论主诉如何修改都不变化。
2. 服务器创建后保存 `serverCaseId`；页面所有保存、恢复、反馈和记录查找都使用稳定 ID。
3. `caseKey` 只作为旧记录迁移输入，不再参与新记录唯一性判断。
4. 新建 `LocalCaseRepository`，提供 `create/list/get/update/delete`，页面不直接按主诉筛数组。
5. 迁移旧记录：每个旧案例入口生成一个 `localCaseId`；已经被旧逻辑合并的历史内容无法可靠拆分，标记 `legacyMerged=true`，不臆测拆分。
6. “新建评估”必须创建新 ID；“继续本案例”追加 `sessionHistory`。

**测试**：相同主诉创建两个案例、修改主诉后继续同案例、同案例多次康复、反馈绑定稳定、旧记录迁移。

**验收**：案例身份只由 ID 决定；文本相同不合并，文本修改不新建。

### DATA-03：取消静默只保留 8 个案例

**实施方案**：

1. 删除 `.slice(0, 8)` 数据截断。
2. 引入浏览器本地仓储接口，优先使用 IndexedDB 保存完整快照，localStorage 只保留迁移标记和极小索引。
3. 案例列表使用分页或“加载更多”，展示全部活动案例和归档案例。
4. 达到浏览器容量限制时，停止新增本地快照并明确提示导出/删除；不能删除最旧数据腾空间而不告知。
5. 将现有 localStorage 数据一次性迁移到新仓储；迁移成功后保留一个版本标记，失败则继续读取旧数据且提示。
6. 服务端已同步但本地快照无法保存时，记录“服务器已保存，本机副本失败”，不要反向显示离线。

**测试**：9、20、100 个脱敏案例列表；容量异常；迁移中断；分页恢复；删除后空间释放。

**验收**：第 9 个案例不会使第 1 个案例消失；容量错误可理解且可恢复。

### DATA-04：创建案例幂等

**推荐设计**：客户端生成 `clientCreationId` 和 256 位随机访问令牌；服务器只保存令牌 hash，并以 `clientCreationId` 唯一约束实现重放。这样创建响应超时后，客户端可安全重发同一组数据，服务器无需保存明文令牌。

**实施步骤**：

1. migration 给 `pilot_cases` 增加 `client_creation_id` 唯一列；旧数据回填独立值。
2. 客户端在首次创建前生成并持久化 `clientCreationId` 与 access token，重试必须复用。
3. 创建 API 校验 UUID、token 长度和随机强度格式；服务端计算 hash。
4. repository 先按 `clientCreationId` 查询：不存在则事务创建；存在且 token hash 一致则返回原案例；不一致则冲突。
5. 响应增加 `replayed`，用于日志和测试，不向用户显示技术细节。
6. 创建成功但客户端未收到响应时，下次同步先重放创建，再保存进度。

**测试**：同请求连续两次、第一次响应丢失、并发两次、相同 creationId 不同 token、不同 creationId 相同主诉。

**验收**：任何重试只产生一个案例、一条 `case_created` 事件和一个初始快照。

### DATA-05：完整快照 schema 与迁移

**实施步骤**：

1. 将 `SavedDemoSnapshot` 从主组件移到 `app/persistence/pilot-snapshot-schema.ts`。
2. 增加顶层 `schemaVersion`，从 `1` 开始；定义运行时 schema，建议使用单一结构化校验库，不写零散 `in` 判断。
3. 为每个字段声明类型、默认值、枚举和上限；未知字段可在同版本保留，但关键字段缺失必须拒绝。
4. 建立 `migrateSnapshotV1ToV2` 等纯函数链；迁移不直接修改原对象。
5. 恢复顺序固定为：解析 JSON → 识别版本 → 迁移副本 → 完整校验 → 构建页面状态。
6. 损坏或未来版本显示恢复错误，提供保留原始副本/导出诊断，不自动重置案例。
7. 服务端写入前也校验 schema，不只信任客户端。

**测试**：当前完整快照、每个历史版本、缺字段、错枚举、未来版本、超深对象、损坏 JSON、迁移幂等。

**验收**：`isSavedDemoSnapshot` 不再只检查 `step/intake`；不兼容数据不能进入页面半恢复状态。

### DATA-06：可操作的冲突处理

**实施步骤**：

1. 新建独立 `PilotConflictDialog`，输入本地和远端的 revision、保存时间、阶段和内容摘要。
2. 第一版不做自动字段级合并，只提供：读取远端、保留本地并在远端最新 revision 上另存、导出本地副本、取消。
3. “保留本地”必须先重新读取远端 revision，再以用户明确确认的本地快照覆盖；写入 `conflict_resolved` 事件。
4. “读取远端”先把本地副本放入可恢复的冲突备份，再替换页面状态。
5. 冲突期间禁用普通保存，避免重复 409 循环。
6. 冲突完成后更新 hash、revision、dirty 和 UI 状态。

**测试**：两个窗口分别修改、重复冲突、远端在对话框期间再次变化、取消后本地仍在、两种选择的事件记录。

**验收**：用户每个选择的后果明确；没有静默覆盖和死循环。

### SAVE-01：实现真实自动保存并校正文案

**边界**：本地草稿可高频自动保存；服务器只在稳定检查点或防抖后同步，避免每个按键写 D1。

**实施步骤**：

1. 抽取 `usePilotPersistenceController`，页面只提交结构化状态和业务事件。
2. 本地状态变化后 500 至 1000ms 防抖保存草稿；关键导航前立即 flush。
3. 服务器在完成字段、切换阶段、处理/复测提交、训练反馈和手动保存时同步；连续变化可 2 至 3 秒防抖合并快照，但事件不能被错误吞并。
4. 保存状态机统一为 `local-saving/local-saved/syncing/synced/offline/conflict/error`。
5. 文案准确区分“已保存到本机”“已同步服务器”“等待连接”“发生冲突”。
6. 页面刷新先恢复最后成功本地草稿，再按 DATA-01 规则与服务器协调。
7. `beforeunload` 只做尽力提示，不把它当作唯一保存机制。

**测试**：输入后刷新、阶段切换中刷新、断网填写、恢复网络、服务器超时、冲突、浏览器禁止存储。

**验收**：页面关于保存的每句承诺均可由实际场景证明；不再只在用户点击最终保存时留存。

### FEED-01：反馈精确关联案例、康复记录、模块和事件

4. 提交反馈时事务写 `case_feedback` 和 `feedback_submitted` 事件。

**测试**：当前模块反馈、事后反馈前一模块、前一次康复、未定位、跨案例 eventId、目标事件删除后的保留行为。

**验收**：后台能回答“用户在哪次康复、反馈哪个模块/操作、提交时位于哪里”。

### OPS-01：脱敏、可关联的结构化错误日志

**实施步骤**：

1. 每个请求生成 `requestId`；客户端可传 traceId，但服务端校验格式并生成最终 ID。
2. 日志固定字段：timestamp、level、code、route、requestId、内部 caseId 或其稳定 hash、eventId、revision、release versions、duration、outcome。

5. 客户端错误提示显示可复制的短 requestId，方便粉丝群反馈。
6. 预览环境通过 Cloudflare 日志出口验证 4xx、409、500；正式环境设置保存期限和访问权限。
7. 对日志 sanitizer 做敏感字段变体和嵌套对象测试。

**验收**：凭 requestId 可从反馈定位请求和版本；任何日志和响应都不含访问秘密或完整健康正文。

## 9. 隐私、安全、版本与部署整改

### PRIV-01：服务端存储前的知情提示和同意记录

**需要产品负责人先确认**：数据用途、保留期限、联系方式、删除方式和试用范围。执行者不能自行决定法律文本或期限。

**实施步骤**：

1. 建立版本化 `pilot-consent` 文案，说明收集内容、用途、非 AI 决策、访问范围、保留/删除和反馈方式。
2. 用户首次远端建案前显示独立同意步骤；未同意仍可使用允许的本地功能，但禁止上传。
3. 数据表记录 `consent_version/consented_at/consent_scope`，或建立 append-only consent 事件与独立列供快速查询。
4. `case_created` 与 `consent_confirmed` 的顺序必须可解释；推荐先以不含健康正文的创建意图记录同意，再创建正式案例。
5. 文案版本变化时，已有用户在下一次远端写入前重新确认重大变化。
6. 后台显示同意版本和时间；导出/删除流程包含该记录的保留规则。

**验收**：未同意无法上传；同意版本可追溯；撤回后停止新写入并进入删除/保留流程。

### PRIV-02：明确软删除和最终清除

**需要负责人确认**：活动案例期限、软删除宽限期、反馈/审计记录是否单独保留、备份期限。

**实施步骤**：

1. 将保留策略写成配置和用户说明，不把期限散落在代码。
2. 用户删除后立即使访问 token 失效、状态改为 `deleted`，正常读取返回统一不可用结果。
3. 增加 `purge_after`；定时任务删除到期快照、事件、反馈和案例，或按获批策略匿名化必须保留的统计。
4. 管理员只能在授权宽限期查看删除状态；任何恢复动作必须审计。
5. 备份恢复后再次执行删除清单，避免已删除案例复活。
6. 提供定期 purge 报告，只含数量和失败 ID，不含正文。

**验收**：删除后旧链接立即失效；到期后数据库不可检索；备份恢复演练不恢复已过期数据。

### SEC-01：请求大小、频率和滥用防护

**实施步骤**：

1. 为创建、保存、反馈、读取和管理员接口分别定义 body 上限、字段长度、数组数量、嵌套深度和允许 content-type。
2. 在读取 JSON 前检查 `Content-Length`；缺失或不可信时使用带上限的流读取，超过即返回 413。
3. 建立 `PilotAbuseGuard` 接口，Cloudflare 实现按 IP hash、invite hash、caseId 和 route 组合限流；原始 IP 不写业务日志。
4. 创建与反馈采用更严格频率；正常保存允许短时突发但限制持续速率。
5. 邀请失败使用统一响应和近似耗时，避免透露 token 是否过期/撤销。
6. 管理接口增加更严格限流、短期会话、CSRF 防护和安全响应头。
7. 设定告警阈值：大量 403、413、429、重复创建或单案例异常写入。

**测试**：边界大小、超大 JSON、深层对象、高频请求、并发突发、不同案例隔离、管理员暴力尝试。

**验收**：恶意请求不会造成无界 D1 写入、内存增长或敏感差异响应；正常一次康复不误限流。

### REL-01：单一版本来源与快照 schemaVersion

**实施步骤**：

1. 新建构建期版本生成器，从 package version、知识库版本、决策版本和 commit SHA 生成只读 release manifest。
2. `src/infrastructure/pilot/release/release-version.ts` 改为读取生成 manifest，不再手工硬编码三处 `0.1.0`。
3. 每个快照和事件写入 `schemaVersion`；案例继续保存创建时版本，事件保存发生时版本。
4. 发布时向 release 表 upsert manifest、构建时间和 migration 版本。
5. 页面页脚/问题反馈显示短版本；管理员显示完整 manifest。
6. 构建阶段检查版本为空、dirty 工作树发布、知识/决策版本未更新等错误。

**验收**：同一构建在页面、案例、事件、日志和后台显示一致版本；旧快照按 schema 迁移。

### REL-02：使发布可从干净检出复现

**实施步骤**：

1. 审查当前未跟踪 API、D1、Wrangler、脚本和文档，分类为应提交、生成物或秘密。
2. 更新 `.gitignore`，只忽略可重建产物和秘密；关键 migration、配置模板和测试必须提交。
3. 增加 `npm ci → typecheck → lint → tests → build` 的干净检出验证。
4. 部署脚本记录 commit、lockfile hash、Wrangler 版本、migration 和目标环境。
5. 发布前工作树必须干净，或者显式阻断；不允许从个人未提交文件部署。
6. 编写回滚说明：上一 Worker 版本、兼容的 schema 范围和数据前向兼容策略。

**验收**：在新目录从仓库检出后，无手工复制文件即可构建、创建本地 D1、运行测试和部署预览。

### DEPLOY-01：预览与正式环境彻底隔离

**实施步骤**：

1. 使用 Wrangler `env` 或独立配置定义 `preview` 与 `production`；名称、URL、D1、邀请、管理员 secret 和日志标签全部不同。
2. 当前 `rehabmind-preview` D1 只能绑定预览 Worker；正式环境创建独立 D1。
3. 页面明显显示非正式环境标识；案例和日志保存 `environment`。
4. migration 命令要求显式环境参数，并在执行前打印 Worker、database_name、database_id 和待执行 migration，要求人工确认正式环境。
5. 预览邀请和管理员密钥不得复用于正式环境。
6. 部署顺序固定为：备份 → migration dry check → migration → Worker 发布 → health → P0 preview → 标记版本。
7. 正式环境发布必须引用已经通过预览的同一 commit 和 release manifest。

**验收**：在预览创建的数据不能从正式读取；误用配置会被脚本阻断；两个环境版本清晰可见。

## 10. 架构、管理、素材与可访问性整改

### ARCH-01：拆分 8000 行主组件和持久化耦合

**策略**：采用逐步替换，不整体重写页面。每提取一个模块先做行为等价测试，再切换调用，最后删除旧分支。

**目标边界**：

```text
app/workflow/        纯状态、阶段迁移、依赖失效
app/decision/        现有决策核心和适配器
app/persistence/     本地仓储、快照 schema、同步、冲突
app/pilot/           API 合同、事件、反馈、版本
app/features/intake/
app/features/assessment/
app/features/treatment/
app/features/retest/
app/features/training/
app/features/summary/
app/components/      通用页面与弹层组件
```

**实施步骤**：

1. 先提取无 UI 的快照构建/恢复和 persistence controller，解决 DATA/SAVE 问题。
2. 将 38 个离散状态按领域收敛为 reducer/state machine；事件使用业务名称，不暴露 setState 组合。
3. 提取阶段依赖失效函数，统一返回修改、权限撤销、加重和新症状后的清理范围。
4. 逐步提取 Intake、Safety、Assessment、Treatment/Retest、Training、Summary 容器；容器只接收领域状态和 command。
5. 决策核心保持纯函数，页面不得复制候选筛选规则。
6. 每完成一阶段，运行该阶段规则测试、快照往返、固定浏览器和视觉回归。
7. 最后删除重复旧分支；构建分析确认主 chunk 和组件复杂度下降。

**验收**：主页面负责路由和布局，不直接操作 localStorage/API，不包含事件序列生成；核心状态可脱离 React 测试。

### ADMIN-01：建立小规模试用管理工作台

**范围**：前期只做案例检索、时间线、反馈分流、版本查看和删除，不扩展成完整医疗后台。

**实施步骤**：

1. API 增加游标分页、publicCode 精确检索、状态/版本/时间/反馈状态筛选和排序。
2. 管理员密钥只用于建立短期 HttpOnly、Secure、SameSite 会话；不把长期 key 保存在浏览器 localStorage。
3. 新建受保护 `/admin`：案例列表、案例详情、康复记录、事件时间线、反馈、版本和删除状态。
4. 反馈支持 `new/triaged/reproduced/resolved/wont_fix`，记录管理员备注和操作事件。
5. 详情默认显示脱敏摘要，查看完整快照需要额外确认并记录审计。
6. 导出仅提供脱敏 JSON/CSV；真实健康正文导出必须另行授权，不在首版默认开放。
7. 删除、反馈状态修改和备注都写 admin 事件。

**测试**：未登录、过期会话、案例 token 越权、分页稳定、筛选、反馈流转、删除案例、键盘操作。

**验收**：管理员可凭案例编号定位完整流程和反馈，不需要直接调用 API 或查询 D1。

### CONTENT-01：真人动作素材与审核清单

**实施步骤**：

1. 建立机器可读 asset manifest：actionId、self/pro、文件、真人/示意类型、来源、授权、拍摄日期、审核人、审核状态、尺寸、hash 和替代文本。
2. 正式处理/训练卡只允许 `approved` 且类型符合产品要求的素材。
3. 当前 12/27 动作逐项复核；`K-A05 self`、`A-M04` 等已知问题保持禁用直到专业复核。
4. 缺失动作按首发路径优先拍摄/采购；每张图检查姿势、接触区域、方向、器材、隐私和裁切。
5. 不合适的 SVG 只可保留在定位示意等正式规范允许的位置，不能冒充真人动作演示。
6. 构建脚本校验 manifest、文件 hash、缺失配对和未审核引用。
7. 视觉测试确认不同视口下主体完整、文字不遮挡、self/pro 不串图。

**验收**：正式试用路径没有未审核占位图；素材来源和专业审核可追溯。

### UX-01：弹层焦点、键盘和可访问性

**实施步骤**：

1. 新建共享 `DialogShell`，统一标题关联、描述、初始焦点、焦点锁定、Escape、关闭后焦点恢复和背景不可交互。
2. 教程、案例记录、问题反馈和移动摘要逐个迁移，不在各组件重复实现。
3. 图形选择器和自定义按钮确保可见焦点、键盘激活、选中状态和可访问名称。
4. 错误信息使用 `role=alert`；保存状态使用不过度打扰的 live region。
5. 关闭按钮使用清晰图标和可访问名称；鼠标点击背景关闭不得导致误操作。
6. Playwright 增加 Tab 顺序、Shift+Tab、Escape、焦点恢复和背景不可聚焦测试。
7. 人工使用键盘完成教程、主诉、反馈和案例恢复。

**验收**：不使用鼠标可以完成所有关键弹层任务；焦点不会丢到页面背后。

## 11. 批次级迁移、回退和发布

### 11.1 每个数据库批次

1. 从上一 schema 建立临时 D1。
2. 导入脱敏代表数据：空案例、进行中案例、多次康复、反馈、删除案例和冲突案例。
3. 执行新 migration。
4. 运行仓储合同、API 集成和快照读取。
5. 使用旧应用读取新 schema 的兼容部分，明确是否可以应用回滚。
6. 若 schema 不可回滚，应用回退必须使用兼容层，不能直接部署完全不认识新列/新版本的旧代码。

### 11.2 每个前端/流程批次

1. 运行受影响的规则和状态测试。
2. 运行绑定的固定浏览器场景。
3. 运行历史缺陷回放集。
4. 运行 P0 浏览器套件。
5. 涉及布局则运行视觉基线。
6. 在本地保留旧实现开关只限一个发布周期；行为稳定后删除，避免双重逻辑长期存在。

### 11.3 预览发布验收

- migration 和 release manifest 一致；
- 创建、自动保存、刷新恢复、多案例隔离和冲突通过；
- 事件、反馈和 requestId 可在后台定位；
- 邀请、案例 token 和管理员会话相互隔离；
- 删除与失效链接符合保留策略；
- 日志经过脱敏检查；
- P0 浏览器场景连续三次；
- 普通用户和专业人员任务式走查完成；
- 所有 P0 为“已通过”，P1 未通过项有明确阻断或风险接受记录。

## 13. 需要项目负责人确认的事项

以下事项不能由执行者擅自决定，进入对应批次前集中确认：

1. 服务端健康相关数据的用途说明和同意文案。

这些确认项应形成书面决定并更新相应正式文档或运营说明；在确认前可以完成技术接口和配置能力，但不得填入执行者自创的业务数值。
