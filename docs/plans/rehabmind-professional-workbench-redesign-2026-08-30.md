## 一、目标形态（2026-08-29 owner 确认）

```text
┌──────────────────────────────────────────────────────────┐
│ 案例栏：主诉原话｜部位｜侧别｜性质｜时间｜安全状态｜本次目标   │
├────────────────┬──────────────────────┬──────────────────┤
│ 本次评估（主区）  │ 当前异常与处理计划       │ 待复查项目         │
│ 基础检查（完成态） │ 当前异常（评估确认）      │ 处理对应复查        │
│ 高频检查         │ 处理方向/已完成处理       │ 主诉复查           │
│ 可追加检查        │ 处理对应证据             │ 复查结果           │
├────────────────┴──────────────────────┴──────────────────┤
│ 本次记录：继续评估｜完成处理｜集中复查｜保存并结束              │
└──────────────────────────────────────────────────────────┘
```

owner 裁定要点（2026-08-29 会话）：
1. **本次评估的内容是最有价值的，排版着重凸显**。
2. 主诉由专业人员填写，可靠性高，可直接用于评估分支选择（但仍不能绕过实际评估生成处理）。
3. 不展示：全部评估目录、历史频率、完整规则图、规则 ID、内部排序分数。
4. 专业模式不是普通模式的逐步问答版本。

## 三、文案与视觉原则（owner 2026-08-30 补充裁定）

**总要求：简洁风格，文字不冗余复杂，用户看得懂、读起来不累。**

### 文案六规则

1. **一句一件事**：每条说明只讲一件事，不超过两句；条件多就拆清单，不写长句。
2. **动词开头**：直接告诉用户做什么（"复查膝伸直"），不解释系统为什么这么做。
3. **数字与状态代替描述**：写"已记录 3/5"，不写"大部分已完成"；写"右侧伸直少约15°"，不写"存在一定程度的受限"。
4. **零实现语言**：用户可见层不出现"快照、投影、基线、线程、门控、证据链、候选、修订"等词——专业模式也不出现（专业保留的是临床术语，不是系统术语）。
5. **同屏不重复**：标题、正文、小字三层不说同一件事；一句解释只出现一次。
6. **安全信息不减字**：停止、就医、转介提示的条件和出口必须完整，不受"精简"影响。

### 两种模式的"简洁"含义不同

| | 普通模式 | 专业模式 |
|---|---------|---------|
| 语言 | 通俗人话，避免临床术语 | 标准临床术语，精确但不堆砌 |
| 示例（评估提示） | "先做这 4 项检查" | "主诉：下楼时膝内侧疼。先查：伸直、屈曲、下蹲复现" |
| 示例（异常显示） | "伸直比另一边少一些，处理后要再试一次" | "伸直：右侧较健侧少约15° → 处理后复查伸直" |
| 示例（处理卡） | "在大腿外侧轻柔放松30～60秒，再试下楼" | "大腿外侧链松解 → 复查：伸直、下蹲" |

### 视觉规则

1. 每屏一个主任务：工作台首屏的主任务只有"完成本次评估"；处理/复查次之。
2. 完成态折叠：已完成的检查/复查折叠为计数条（"已完成 3/5"），点开才展开明细。
3. 留白分层：区块之间用间距分层，不靠边框和底色堆叠；卡片内不超过两层嵌套。
4. 按钮限量：每屏主按钮最多 1 个，次级按钮不超过 3 个。
5. 图标与标签优先于长文字：状态用"✓ 已记录 / · 待记录"，不写整句状态描述。

## 四、改造项（按批实施）

### 批次 1：评估段工作台补全（对齐 8.29 形态）

1. **新增案例栏组件**（主诉摘要+编辑入口）：原话、部位/侧别、性质、onset/受伤场景、安全状态、本次目标；提供"修改主诉"入口（跳现有主诉编辑， professionals 直接补信息）。数据全部来自现有 intake/safety，无新事实源。不展示 capabilitySnapshotId 等内部审计标识。
2. **本次评估主区支持两种记录方式**：逐项打开（现有）+ **集中记录**（同类检查同屏批量录结果，如四个方向的活动度一屏记完）。8.29 裁定"允许专业人员批量记录结果、不强迫逐题流程"——这是专业模式的核心交互差异，必须落地；实现先从同 kind 项的集中表单开始。
3. **三栏改四区**：本次评估（主区，占约 1/2 宽）/ 当前异常与处理计划 / 待复查项目 / 专项检查（并入评估区尾部"可追加检查"，保留权限状态显示）。
4. **排版凸显**：评估区放大置左；异常/复查两栏窄列置右；完成态项目折叠为计数。
5. **学习解释**：`learningExplanation` 保留现有行为（finding 备注里显示），工作台不新增位置。
6. 数据来源全部复用：`assessmentDisplayItems`、`findings`/`problemLedger`、`trialRecords`、复查台账投影（`projectRetestLedger`）。无新增事实、无 schema 变更。

### 批次 2：处理与复查段工作台化

1. 处理复测阶段（step 3）提供同一工作台视图：处理队列（当前目标/候选/已完成）、复查义务（pending/completed）、继续排查建议卡（切片①已产出）集中于右侧两栏。
2. 底部动作条按阶段渲染：继续评估（回评估，走既有 RETURN-EDIT 通道）｜完成处理｜保存并结束。"集中复查"动作第一版不做独立入口——复查已嵌入处理流，避免出现语义含糊的第二复查入口；若试用后确有需求再立项。
3. 双侧场景在工作台中的呈现（bilateral-assessment-ledger 的左右状态）在批次 2 设计时细化，本方案不展开。
4. 普通模式零影响：thinking 专属视图，guided 路径不渲染。

### 批次 3（可选，视批次 1/2 试用效果决定）

训练与总结阶段是否也需要工作台入口目前**不能证明必要**：这两段专业人员操作密度低。默认不做；若试用后确有概览需求，作为只读入口补充。移动端适配（820px 断点以下单列）随批次 1/2 各自落地，不单独成批。

### 明确不做

- 不重写决策内核（Command/聚合根仍按原计划独立推进）。
- 不做账户/订阅/服务端规则执行（APK 阶段另议）。
- 不展示内部频率、规则 ID、完整评估目录（防抄袭边界不变）。
- 普通模式（guided）零改动。

## 五、拍板点决议（owner 2026-08-30 已定）

1. **批次拆分**：拆两批实施（评估段 → 处理复查段），验收节奏独立。
2. **专项检查位置**：✅ 选 A——并入"本次评估"区尾部作为"可追加检查"段，不设独立栏；权限状态显示保留在段落头部。

5. **文案与视觉**：按第三节六规则+五规则执行；示例风格已获 owner 认可方向。

## 六、风险与边界

- 实施时继续遵守提交边界：QA 未提交改动集中在 tests/、docs/quality、inspect-local.mjs、release.generated.ts，与工作台组件（assessment-stage / workbench-support / 样式）不重叠，但提交前仍逐文件核对。
- 处理复查段工作台化（批次 2）会触碰 treatment-retest-stage 的大量 props——建议届时先做只读投影，再迁移操作入口，分两个提交。
- 继续排查建议卡（切片①）在专业模式下的呈现位置随批次 2 一起落位。
- 测试交接：批次 1 完成后即可交测试会话补专业模式用例，不必等批次 2。
- **集中记录表单的边界**：批量录入的每条结果仍必须走既有评估记录链（同 id、同修订、同完成判定），不得为批量形态另建平行记录结构——否则违背单一事实源。
